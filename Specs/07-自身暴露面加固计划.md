# 07 · 网关自身暴露面加固计划

> **结论先行**：问题不在"vault 存得安不安全"，而在"**谁能读它**"。
> vault 层实现扎实；**读取 vault 的入口默认不设防**。
> 更严重的是同一个原因波及全部 `/v1/*` 代理端点——默认配置下这是一个
> **对外开放、携带上游凭据、能还原原文**的服务。
>
> 本文全部结论均经代码核对，附文件与行号，无推测。

## 0 · 先纠正一个初判

**核对代码后，这个判断不成立。** vault 层做得比我预期好：

## 2 · 风险清单

### P0-1 · 控制面默认无鉴权，且波及全部代理端点

```go
// internal/server/server.go:137-141
func (s *Server) authMiddleware(next http.Handler) http.Handler {
	if s.authTok == "" {
		return next          // ← token 为空时完全放行
	}
```

```go
// internal/config/config.go:148-152 —— Default() 的 Gateway 段
Gateway: GatewayConfig{
	Listen:         ":8400",
	Upstream:       "https://api.openai.com",
	RequestTimeout: 30 * time.Second,
	Debug:          true,
	LogLevel:       "info",
},                               // ← 没有 AuthToken 字段，默认空字符串
```

```go
// internal/server/server.go:57 —— 中间件包住的是整个 mux
return s.authMiddleware(s.mux)
```

受影响的端点（`internal/server/server.go:61-72`）：

| 端点 | 无鉴权时的后果 |
|---|---|
| `/v1/chat/completions`、`/v1/completions`、`/v1/embeddings`、`/v1/responses`、`/v1/messages` | 任何能连到端口的人可**用你配置的上游 API key**（`Upstream.APIKey`）调用上游 |
| `/v1/privacy/restore` | 按 `request_id` **还原原文** |
| `/v1/privacy/redact` | 配合 `gate_only` 回显命中原文（见 P1-1） |
| `/metrics`、`/healthz` | 内部指标外泄 |

`SECURITY.md` 自述：「凭据/对话内容泄漏视为 P0 事件，响应窗口以**天**计」。
本项同时命中"凭据"与"对话内容"两条。

**为什么这是默认值问题而非配置问题**：`auth_token` 是可选字段，`Default()` 从不设置它，
而配置了上游 key 却没配 `auth_token` 是一个很自然的组合（用户按 README 配好上游就能跑）。
⇒ **多数部署会落在无鉴权状态**，且不会收到任何提示。

### P0-2 · `request_id` 客户端可控 + 写入无冲突检测

```go
// internal/proxy/proxy.go:690-698
func requestID(r *http.Request) string {
	if v := r.Header.Get("X-Request-ID"); v != "" {
		return v                              // ← 直接采用，不校验格式/长度
	}
	if v := r.Header.Get("X-Llmate-Request-Id"); v != "" {
		return v                              // ← 同上
	}
	return randHex(16)                        // 这一路是 crypto/rand，本身没问题
}
```

```go
// internal/vault/vault.go:112-114
v.mu.Lock()
v.tables[table.RequestID] = table             // ← 后写覆盖，无冲突检测
v.mu.Unlock()
```

两个独立后果：

- **(a) 覆盖写入**：攻击者可用已知 `request_id` 覆盖他人映射表，污染还原结果
- **(b) 越权读取**：若生产客户端使用可预测的 `request_id`（固定值、时间戳、用户 ID 派生），
  叠加 P0-1（无鉴权）即为**直接的越权还原通道**

注意 (b) 的成立条件是"客户端用了可猜 ID"。这取决于调用方实现，**网关侧无法假定安全**。

### P1-1 · `gate_only` 把命中原文回显给调用方

```go
// internal/proxy/privacy.go:67-70
// entitySummary 极简 PII 实体摘要（gate_only 模式用，不含 start/end 避免泄漏结构）
type entitySummary struct {
	Type  string `json:"type"`
	Value string `json:"value,omitempty"` // 命中字符串本身（用于 hooks 决定「拦还是脱敏后放」）
}
```

设计意图清楚——给 hooks 判断"拦还是脱敏后放"。但叠加 P0-1 后，
网关同时成为一个**PII 提取接口**：任意调用方提交文本 + `gate_only:true` 即得命中原文。

`gate_only` 默认 `false`（`internal/proxy/privacy.go:50`），需显式开启，这一点是好的。

### P1-2 · `persist` 是单向无效功能

```go
// cmd/llmate-gate/main.go:75
v, err := vault.NewMemVault(cfg.Vault.RequestTTL, nil, cfg.Vault.Persist, cfg.Vault.Path)
//                                               ^^^ passphrase 恒为 nil
```

```go
// internal/vault/vault.go:59-64 —— 传 nil 时每次启动生成随机密钥
if len(passphrase) == 0 {
	passphrase = make([]byte, 32)
	if _, err := io.ReadFull(rand.Reader, passphrase); err != nil { ... }
}
```

```go
// internal/vault/vault.go:129-141 —— Get 只查内存 map，从不读磁盘
func (v *MemVault) Get(requestID string) (*types.MappingTable, error) {
	v.mu.RLock()
	t, ok := v.tables[requestID]
	v.mu.RUnlock()
	...
}
```

⇒ 配置 `persist: true` 时：

1. 落盘文件用**本次进程的随机密钥**加密
2. 重启后密钥不同，且 `Get` 根本不读磁盘 ⇒ **文件永远解不开、也永不会被读到**
3. 磁盘上持续累积不可解密的 `.lmgv` 文件

`VaultConfig` 里**没有任何密钥字段**（`internal/config/config.go:130-136`），
所以目前不存在"配好密钥让 persist 生效"的路径。

**性质**：这不是数据泄漏，是**假安全感 + 可用性缺陷**。
风险在于有人据此认为"我已持久化"，实际重启即丢。

### P2 · 审计日志无轮转

`internal/audit/audit.go` 中检索不到 `rotate` / `MaxSize` 等逻辑。
单个 `./audit.log` 无限增长。默认 `LogPII: false` 且有测试守卫
（`internal/config/config_test.go:54` 断言"审计默认不含原文"）——这一点做对了。
但若用户打开 `log_pii`，原文会长期堆在单一文件里，无轮转、无加密。

## 3 · 处置方案

### 阶段 A —— 闭合 P0（先做，改动小、收益最大）

| # | 动作 | 改动面 | 说明 |
|---|---|---|---|
| A1 | 让"无鉴权启动"不可能静默发生 | `config.go` + `main.go` | 见 §5 待拍板 |
| A2 | `requestID` 加格式校验 | `proxy.go:690-698` | 白名单 `[A-Za-z0-9_-]{8,64}`；不合法则回退 `randHex(16)` |
| A3 | `vault.Put` 拒绝覆盖未过期条目 | `vault.go:102-126` | 冲突时返回错误或换新 ID，不静默覆盖 |

**A1 的三种实现选择**（详见 §5）：拒绝启动 / 自动生成并打印一次 / 保持现状但打醒目告警。

### 阶段 B —— 收敛控制面

| # | 动作 | 改动面 |
|---|---|---|
| B1 | `gate_only` 默认不回显 `value`，改为按需开关 | `privacy.go` + 契约 §2.3 |
| B2 | 控制面（`/v1/privacy/*`）与数据面（`/v1/*`）分离鉴权 | `server.go` + `config.go` |

B2 的理由：控制面能还原原文，数据面只转发。两者值得不同级别的凭据。

### 阶段 C —— 处理 `persist`

两条路，倾向后者：

- **C1 修好**：补 `vault.key` 配置项（支持 `${ENV}` 展开，项目已有 `expandEnv`）+ 启动时从磁盘加载
- **C2 删掉**：移除 `persist` 选项，配置了就直接报错启动失败

C2 的理由：当前是假功能；在密钥管理方案（轮换、KMS、备份）没想清楚前，
"能持久化原文"比"不能持久化"更危险。**先删掉假安全，需要时再正经设计。**

### 阶段 D —— 可观测性

| # | 动作 |
|---|---|
| D1 | 审计日志加轮转（大小或按天） |
| D2 | 启动时若检测到关键安全项未配置，打醒目 WARN |

## 7 · 实施记录（2026-09-16）

阶段 A → B → C → D 已全部落地。改动**只碰入口与配置层，未动检测/替换/加密核心**。

### 7.1 拍板结果

| # | 问题 | 结果 |
|---|---|---|
| 1 | `auth_token` 为空 | **(b)** 自动生成随机令牌并打印一次 —— 并补强「落盘 + 跨重启稳定」，见 §7.2 |
| 2 | `persist` | **(a)** 删掉（配置即启动失败） |
| 3 | `gate_only` 回显 | **(a)** 默认不回显 `value`，加 `include_values` 显式开关 |
| 4 | 阶段顺序 | A → B → C → D |

### 7.2 对 (b) 的一处必要补强（与原方案有差异，需知悉）

原方案 (b) 是「生成随机令牌并打印一次」，但**只生成在内存里**有一个致命缺陷：

> 每次重启换一个令牌 ⇒ 客户端（Claude Code hooks / VS Code 扩展）全部 401 ⇒
> 用户配好一次、重启又要再配 ⇒ **最终选择关掉鉴权，反而比改动前更不安全**。

因此实现改为：生成后写入 `gateway.auth_token_file`（默认 `./auth_token`，`0600`），
**重启复用同一个令牌**。首次生成时打印令牌值与文件路径，后续启动只打印来源。
客户端只需配置一次。

这一条超出原始拍板范围，如需回退为「仅内存生成」，改 `config.ResolveAuthToken` 的落盘分支即可。

### 7.3 关键设计取舍

**「没配 `auth_token`」不再等于「不鉴权」。** 两者必须分开：

| 意图 | 配置 |
|---|---|
| 我还没配 | 什么都不写 → 自动生成令牌（默认安全） |
| 我明确不要鉴权 | `allow_unauthenticated: true` → 启动日志打 SECURITY WARNING |

为什么不能沿用「空值即放行」：无鉴权 + 已配 `upstream_api_key` = 任何能连到端口的人
都能用你的凭据调上游。这个组合太容易「因为忘写」而产生，不能让它静默发生。
`configs/bench-gate.yaml`（CI 用）已改为显式声明。

**`/healthz` 保持不鉴权**：探针通常不持凭据（`scripts/install.sh`、`ci.yml`、VSCode 扩展
均匿名探测），强制鉴权会让「服务没起来」和「没带令牌」混成同一个 401。代价是暴露
detector 可用性，不含请求内容或凭据。

**控制面与数据面分令牌**：控制面能还原原文，数据面只转发。
`control_auth_token` 留空时回退数据面令牌，单令牌部署行为不变。

### 7.7 仍未处理

- ~~**调试面板**（`/_debug`、`/_api/*`）挂在数据面 mux 上，用数据面令牌。~~ → 已在 §8 处理
- ~~**P0-2 (b) 越权读取**~~ → 已在 §8 处理（来源隔离）
- **审计文件轮转后无归档/加密**：轮转只解决「单文件无限增长」，历史文件仍是明文
  （`log_pii=false` 时不含原文）。
- **面板 Cookie 的传输未加密**：面板是 loopback 上的明文 HTTP，令牌以 Cookie 承载时
  不带 `Secure`（带上就在 HTTP 下完全失效）。在回环上可接受，但它意味着「同机能读
  网卡流量的人」可以拿到令牌——而那种人本来就能读 `auth_token` 文件。若将来面板走
  TLS，应把 `Secure` 补上。
- **控制面内部无调用方区分**：控制面令牌是部署级单凭据，因此 A、B 两个调用方共享它时，
  A 仍可还原 B 的 `request_id`。之所以不紧急，是因为控制面的 `request_id` 是 128 位
  随机值（`proxy.newRequestID`），B 不主动泄漏就拿不到；而数据面那条（ID 由客户端指定）
  已经堵死。真要根治需要引入多令牌 + 归属，是独立设计。

### 8.1 越权读取：从「收窄」到「根治」

**问题**：`/v1/privacy/restore` 的入参是一个纯文本 `request_id`，而映射表只按 ID 索引。
数据面的 `request_id` 来自客户端可指定的 `X-Request-ID`（A2 只把它约束成
`[A-Za-z0-9_-]{8,64}` 的**形状**，没有约束**来源**）。于是任何持有控制面令牌的调用方，
只要知道另一个请求的 ID，就能把那次请求脱敏掉的原文取回来——一条绕过 vault 加密、
绕过 TTL 语义、也不经过任何内容审计的读取路径。

**处置**：给映射表加来源标记，还原时按来源校验。

| 建造入口 | `Origin` | 能否经 `/v1/privacy/restore` 还原 |
|---|---|---|
| `/v1/*` LLM 请求（`processor.Store`） | `data` | ❌ |
| `/v1/privacy/redact`（`processor.StoreControl`） | `control` | ✅ |
| 旧数据 / 未标注（空值） | 按 `data` 处理 | ❌ |

三个细节值得记住：

1. **缺省取收紧的一侧**。空 `Origin` 按 `data` 处理。反过来（空值当控制面）会让所有
   历史条目自动获得还原许可，等于把兼容性做成了一个开口。
2. **拒绝的理由统一是 `not_found`（404）**。「存在但你无权还原」若回 403，就等于确认了
   这个 ID 真实存在——一个探针。`AssertRestorableViaAPI` 对「不存在 / 已过期 / 不是控制面
   建的表」返回同一个 `ErrNotFound`。
3. **校验放在 handler 的还原分支之前**，而不是塞进两条还原路径内部：语义一致，将来新增
   分支也不会漏。

顺带修了一处不一致：`statusForCode` 没有 `CodeNotFound` 分支，`not_found` 会被映射成
HTTP 500。已补为 404（`errors.HTTPStatus` 里本来就是 404，两处映射此前是分叉的）。

> ⚠️ **本次只补了「生效的那一份」。** 2026-09-23 复核（`Specs/06` #34）确认：两处映射
> **仍是两份独立实现**，且 `errors.HTTPStatus` / `Response` / `Body` / `ErrorPayload`
> **全仓零调用** —— 平时生效的是 `proxy.statusForCode`。两份在 `CodeNotFound` 上恰好
> 又一致了，但在 `invalid_config` 上**已经再次分叉**（契约函数 400 / 生效实现 500）。
> 读本节结论时**不要**理解为「两处映射已统一」。当前以 `Specs/02` §0.3 的逐码表为准。

### 8.2 调试面板归入控制面

**问题**：`/_debug`、`/_api/*`、`/ws/events` 挂在数据面 mux 上。它们能看到的东西——
流量详情里的请求明文、Playground 的「提交文本→返回其中 PII」、登记表（用户自报的真
实 PII 值）——与 `/v1/privacy/*` 是同一类能力，却只需要「转发用」的数据面令牌。

**处置**：数据端点走控制面令牌；静态壳保持匿名。

| 路径 | 鉴权 | 理由 |
|---|---|---|
| `/_debug`、`/_debug/*` | 匿名 + 回环 | 静态壳不含请求数据，且它是「输入令牌」这个动作的载体——壳本身要凭据就没人能完成第一次认证 |
| `/_api/*`、`/ws/events` | 控制面令牌 | 能读到明文 PII |
| `/v1/privacy/*` | 控制面令牌 | 同上 |
| `/`（数据面）、`/metrics` | 数据面令牌 | 只转发 |
| `/healthz` | 匿名 | 探针通常不持凭据 |

**浏览器怎么带凭据**：浏览器在 `fetch` 与 WebSocket 上都不会带 `Authorization` 头，
所以补了一条 Cookie 通道——访问一次 `/_debug?token=<令牌>` 换取 HttpOnly Cookie，
之后页面里的请求自动带上，**前端零改动**。Cookie 值就是控制面令牌本身，不是第二份
凭据，只是同一份令牌多了一个载体；并且：

- `HttpOnly` —— 前端读不到，XSS 也偷不走；
- `SameSite=Strict` —— 面板不做 CSRF token，这是它的替代；
- 302 重定向回不带查询串的同一路径 —— 令牌不留在地址栏、浏览历史与 Referer 里；
- Cookie 通道**只对面板开放**（`/v1/privacy/*` 仍只认头）—— 最小权限：浏览器里的一次
  会话不该同时是一条「任意 JSON 还原」的通道。

**两层防线而非一层**：`loopbackOnly`（按 `RemoteAddr`，不读 `X-Forwarded-For`）保留不动。
它挡的是「网关绑了 0.0.0.0」，令牌挡的是「同机反向代理把 `RemoteAddr` 变成 127.0.0.1」——
后者是 `loopbackOnly` 看不见的盲区，也是本轮真正的新增覆盖。两者都在，缺一不可。

**启动告警**：`debug=true` 且 `listen` 非回环绑定时打 `SECURITY WARNING`，说明面板暴露的
内容与「回环检查看不穿同机反代」这一事实。绑定地址是空 host（`:8400`，即所有网卡）时按
非回环处理。

### 8.6 环境侧的两项固化

- **Go 工具链**：系统 `/usr/bin/go` 是 1.15.9，编不了本项目（需 1.24+）。用户级安装的
  Go 1.25.13（`~/.local/go`，与 CI 同版本）此前只存在于交互式命令里，已通过
  `~/.zshenv`（覆盖所有 zsh 调用，含非交互脚本）+ `~/.bashrc` / `~/.profile`（bash 与 sh
  登录）引入 `~/.local/share/llmate-gate-dev-env.sh`。四条路径实测生效，重复 source 不
  重复堆 PATH。
- **`TMPDIR`**：本机 `/tmp` 是 10MB tmpfs，Go 链接阶段会以 `no space left on device`
  报错（看起来像磁盘满，其实是 tmpfs 上限，很容易查错方向）。仅在 `/tmp` 确实 < 256MB
  且未由外部设定 `TMPDIR` 时才改，避免影响其它程序。
