> **文档版本**：v1.0
> **受众**：workbuddy（执行体）
> **输入**：`整体技术方案.md`（架构、里程碑、API 契约、仿真规则、安全模型、cn-pii-bench）

## 📖 文档说明

本手册是《整体技术方案.md》的**执行层对应物**。技术方案回答"做什么、为什么"，本手册回答"**怎么一步步做、每一步怎么选最短路径**"。

**使用方式**：workbuddy 每次启动任务时，读取本手册 → 定位到当前 Phase 与任务 → 对该任务执行探路者协议 → 验证 → 更新进度。

## 🎯 全局目标

将 `整体技术方案.md` 落地为可运行的产品 **LLMate Gate**（中文一等公民的 LLM Agent 隐私网关）。

**最终交付物**：

1. 一个监听 `:8400` 的 Go 守护进程（OpenAI 兼容代理）
2. 集成 PII Engineer（Rust/ONNX，中文 F1 0.918）的检测引擎
3. 中文格式保持仿真替换引擎（v1 占位符 → v1.1 仿真）
4. VS Code 扩展 + Claude Code hooks
5. Tauri 桌面 UI
6. cn-pii-bench 基准测试框架
7. 结构化审计日志

---

## 🧭 全局探路（项目级）

在动手之前，先分析整个项目的最短路径：

| 路径 | 方式 | 评估 |
|---|---|---|
| **步行** | 按 Phase 顺序从零写所有代码 | ❌ 慢，且可能走偏——如果中文仿真替换不可行，整个代差不成立 |
| **跳转** | 先做 Phase 0 基准测试，用数据验证代差，再决定后续投入 | ✅ 快，2-3 天出结果，决策风险最低 |
| **直达** | 直接写核心代码，跳过基准测试 | ❌ 赌博，万一竞品中文能力已够强，代差消失 |

**决策**：🥈 **跳转路径**——Phase 0（基准测试）先行，用数据验证代差，再进入 Phase 1。

**理由**：中文仿真替换是产品的 #1 代差。如果 Phase 0 数据证明竞品已覆盖中文，整个方案需要 pivot；先验证，成本最低。

## 🔁 执行 Loop 模板

每个任务（无论大小）必须按以下结构运行：

```
┌─────────────────────────────────────────────┐
│  1. 目标：我要达成什么最终状态？               │
│  2. 探路：列出可能的路径（直达/跳转/步行）      │
│  3. 决策：选择哪条路径？理由？                 │
│  4. 执行：用最高效的方式行动                   │
│  5. 验证：确认目标已达成？                     │
│     └── 若未达成 → 回到 1（调整目标或路径）    │
│     └── 若达成 → 进入下一个任务                │
└─────────────────────────────────────────────┘
```

**Loop 是不退出的**：完成任务不是终点，验证通过才是。验证失败必须回到"目标"或"探路"重新选择。

### Phase 1：代理核心 + 检测引擎（第 3-5 周）

**Phase 目标**：Go 守护进程 `:8400` 可接收 OpenAI 兼容请求，调用 PII Engineer 检测，做占位符替换，转发上游，流式还原。

**Phase 验收**：`curl localhost:8400/v1/chat/completions` 能对含中文 PII 的请求脱敏并还原，流式场景占位符完整还原。

---

#### 任务 1.1：Go 代理骨架

| 步骤 | 探路者协议 |
|---|---|
| **目标** | `go run .` 监听 `:8400`，能接收 `/v1/chat/completions` 请求并转发上游 |
| **探路** | ① **直达**：用 `net/http` + `httputil.ReverseProxy` ② **步行**：手动解析请求再手动转发 |
| **决策** | 🥇 **直达**——`httputil.NewSingleHostReverseProxy` 一行代码搞定转发，专注业务逻辑 |
| **执行** | 写 `gateway/main.go`，配置 upstream，注册 `/v1/*` 路由 |
| **验证** | `curl localhost:8400/v1/models` 返回上游模型列表 |

---

#### 任务 1.2：PII Engineer 集成

| 步骤 | 探路者协议 |
|---|---|
| **目标** | Go 进程调用本地 PII Engineer（Rust/ONNX）做检测，拿到实体偏移 |
| **探路** | ① **直达**：PII Engineer 作为子进程，Go 通过 stdin/stdout 或 Unix socket 通信 ② **跳转**：HTTP 调 PII Engineer 的 `/api/detect` ③ **步行**：Go 重新实现检测逻辑 |
| **决策** | 🥈 **跳转**——PII Engineer 已有 HTTP 服务，Go 直接 `http.Post` 调用，最简单，且无跨进程序列化负担 |
| **执行** | 写 `gateway/detector/client.go`，封装检测调用，返回标准化实体列表（type, value, start, end, score） |
| **验证** | 发含"张三 13800138000"的请求，日志显示检测到 2 个实体，偏移准确 |

---

#### 任务 1.3：占位符替换 + 流式还原

| 步骤 | 探路者协议 |
|---|---|
| **目标** | 请求体中的 PII 被替换为 `<<zh_person_name_1>>`，流式响应中占位符被还原 |
| **探路** | ① **直达**：写 `replace.go` 用偏移量替换，`restore.go` 用 trie 缓冲还原 ② **步行**：正则全局替换 |
| **决策** | 🥇 **直达**——偏移量来自 PII Engineer，直接切片替换；trie 缓冲处理 SSE 流中的 token 边界 |
| **执行** | 实现 `gateway/replacer/` 包：占位符命名规范（`<<zh_person_name_1>>`）、偏移排序替换、trie 流式还原 |
| **验证** | 发流式请求，客户端收到的 SSE 流中占位符被正确还原为原文 |

> ⚠️ **关键技术约束**：占位符长度可能与原文不同，必须用偏移映射而非文本查找；流式场景下 token 可能切断占位符，trie 缓冲必须能跨块拼接。详见技术方案 §6.3。

---

#### 任务 1.4：detection_cache + fail-closed

| 步骤 | 探路者协议 |
|---|---|
| **目标** | 绑定 `conversation_id` 的增量缓存；检测引擎异常时阻断请求 |
| **探路** | ① **直达**：内存 LRU + 内容哈希，键绑定 conversation_id ② **步行**：每次全量检测 |
| **决策** | 🥇 **直达**——内存 LRU 无外部依赖，满足单机场景；键必须含 conversation_id，避免跨会话错复用 |
| **执行** | 写 `gateway/cache/` 包：TTL、conversation 绑定、fail-closed 断路器 |
| **验证** | 同 conversation 第二轮请求检测延迟 < 50ms；人为停掉 PII Engineer 后请求被阻断 |

#### 任务 1.5：内嵌调试面板 + Playground 🔑

> **先探路**：这个面板的实现方式直接决定开发期效率，必须对比三条路径。完整规范见 `UI设计.md`，接口见 `接口与数据契约规范.md` §10。

| 步骤 | 探路者协议 |
|---|---|
| **目标** | `go run .` 后浏览器打开 `localhost:8400/_debug`，实时看到请求原文/检测/脱敏/映射/还原 5 段对比；Playground 可本地即时测试检测与替换，**不发任何请求到上游** |
| **探路** | ① **直达**：Go `embed.FS` 内嵌单页 + WebSocket 推送流量事件，零依赖打进二进制 ② **跳转**：起一个独立 Web 服务（如 mitmproxy UI / Kiji 式 Electron），代理通过本地端口连 ③ **步行**：开发期临时写 curl + `jq` 脚本看日志 |
| **决策** | 🥇 **直达**——`go:embed` 单二进制，`go run .` 即开，开发期零启动成本；且面板**发布保留**（`--no-debug` 可关），不是一次性工具，值得投入。跳转方案需额外进程/端口/CORS，前期摩擦大；步行方案不可复用、无法演示 |
| **执行** | ① 新增 `gateway/debug/`：`handler.go`（路由）、`hub.go`（WS 广播，多订阅者）、`store.go`（环形缓冲 200 条）、`assets/`（HTML/JS/CSS，`go:embed`） ② 在 `internal/pipeline` 关键节点调 `debug.Publish`（非阻塞 + recover 保护，绝不阻塞主流程） ③ 实现 `GET /_debug`、`WS /ws/events`、`POST /_api/detect`、`POST /_api/replace`（纯本地） ④ Playground 前端：输入文本 → 选策略 → 显示实体列表 + 占位符预览 + 仿真预览（v1 置灰） |
| **验证** | ① **D1**：`curl localhost:8400/_debug` 返回面板 HTML ② **D2**：发请求后面板 1s 内显示完整 5 段 ③ **D3**：`lsof`/`netstat` 验证 Playground 点击**不发起任何出站请求** ④ **D4**：Playground 替换结果与 `接口与数据契约规范.md` §5 占位符协议（`<<type_index>>`）一致 ⑤ **D5**：`--no-debug` 启动后 `/_debug`、`/ws/events`、`/_api/*` 全部 404 ⑥ **D6**：面板崩溃（JS 报错）不影响代理正常转发（压测） |
| **关键约束（来自 `UI设计.md` §0.3）** | ① Playground 永不发上游请求 ② `debug.Publish` 非阻塞 + recover ③ 端点默认仅绑定 127.0.0.1 ④ 面板不落 PII 到磁盘（除显式审计导出） |

> 💡 **此任务完成后，Phase 2-4 的所有验证都走面板即时测试**，不再积累 curl 脚本——这是整个项目开发效率的杠杆点。

## 🔄 Loop 控制协议

workbuddy 运行本手册时，必须遵循以下 Loop：

```
┌──────────────────────────────────────────────────────────────┐
│  LOOP START                                                  │
│                                                              │
│  1. 读取整体技术方案.md 的当前 Phase                           │
│  2. 取出该 Phase 的第一个未完成的任务                           │
│  3. 对该任务执行【探路者协议】：                               │
│     a. 目标：这个任务要达成什么？                               │
│     b. 探路：列出 3 条路径（直达/跳转/步行）                    │
│     c. 决策：选最短路径，记录理由                               │
│     d. 执行：动手                                             │
│     e. 验证：检查目标是否达成                                   │
│        ├── 达成 → 标记任务完成，进入下一个任务                   │
│        └── 未达成 → 分析失败原因，回到 b 调整路径               │
│                                                              │
│  4. 每个 Phase 结束时，运行该 Phase 的验收标准                   │
│     ├── 全部通过 → 进入下一个 Phase                            │
│     └── 有失败 → 回到失败的 Phase，诊断并修复                   │
│                                                              │
│  5. 整个项目结束时，运行全局验收（7 项 v1 标准，见技术方案 §15） │
│                                                              │
│  LOOP END                                                    │
└──────────────────────────────────────────────────────────────┘
```

**Loop 的关键不变量**：

- **探路不可跳过**：即使路径明显，也要显式写下三条候选（直达/跳转/步行）——这是避免"惯性选择步行"的核心机制
- **验证不可省略**：每个任务必须有可检查的 Pass/Fail 证据
- **路径可动态切换**：执行中发现更短路径，允许立即跳转，并在 `DECISIONS.md` 记录

## ⚡ 硬性约束（workbuddy 必须遵守）

1. ❌ **禁止在没有探路的情况下直接执行"步行方案"**——每个任务必须先写探路分析
2. ❌ **禁止在可以用一行命令 / 一次调用解决时，选择多步手动操作**
3. ✅ **如果任务包含多个子目标，每个子目标都要独立探路**
4. ✅ **执行过程中如果发现更短的路径，允许立即切换**——探路是动态的，不是一次性的
5. ✅ **每个任务完成后，必须输出验证结果**（Pass / Fail + 证据）

## 🚨 异常处理速查

| 场景 | 探路者响应 |
|---|---|
| PII Engineer 检测延迟 > 500ms | 探路：能否换模型 / 量化？→ 决策：换 INT8 量化，重新测 |
| 竞品中文召回率突然 > 90% | 探路：是否基准太简单？→ 决策：增加对抗样本，重估代差 |
| Go 代理与 PII Engineer 通信失败 | 探路：Unix socket vs HTTP？→ 决策：改 Unix socket 减网络开销 |
| 仿真替换格式不一致 | 探路：Faker zh vs 自定义规则？→ 决策：自定义规则，硬编码校验位算法 |
| 流式占位符跨 token 切断 | 探路：trie 缓冲 vs 整块缓冲？→ 决策：trie 前缀树跨块拼接 |
| 缓存跨会话错复用 | 探路：全局键 vs conversation 键？→ 决策：键强制绑定 conversation_id |
