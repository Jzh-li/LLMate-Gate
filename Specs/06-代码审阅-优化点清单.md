## 🔴 P0-1 · 安装脚本生成的配置 schema 错误

### 现象

`scripts/install.sh`（第 107-119 行）与 `scripts/install.ps1`（第 96-105 行）生成的 `config.yaml` 内容为：

```yaml
gateway:
  listen: ":8400"
  debug: true
upstream:                    # ← 顶层键，不存在
  base_url: "https://api.openai.com"
  api_key: ""                # ← 提示用户「必填」
detector:                    # ← 不存在
  engine: "regex"
replacer:                    # ← 不存在
  strategy: "placeholder"
```

而权威结构（`internal/config/config.go:21-28`）是：

```go
Gateway     GatewayConfig     `yaml:"gateway"`
Detection   DetectionConfig   `yaml:"detection"`
Replacement ReplacementConfig `yaml:"replacement"`
```

正确写法应为 `gateway.upstream`（字符串）、`gateway.upstream_api_key`、`detection.engine`、`replacement.strategy`。**三个顶层键全错**。

`install.ps1:154` 还进一步提示用户：「配置：$cfg（请填 upstream.api_key）」——指导用户去填一个不存在的字段。

### 证据

```
$ cat ~/.local/share/llmate-gate/config.yaml     # install.sh 实际产物
gateway:
  listen: ":8401"
  debug: true
upstream:
  base_url: "https://api.openai.com"
  api_key: ""            # 必填：上游 LLM API key
detector:
  engine: "regex"
replacer:
  strategy: "placeholder"
```

### 影响

用户按安装脚本的提示填写 `upstream.api_key`，网关**静默忽略**该字段，实际使用 `gateway.upstream_api_key`（默认空）转发，上游返回 401，用户无法从任何日志看出原因。

当前之所以没暴露，是**巧合**：错误键的所有默认值恰好等于期望行为（`gateway.upstream` 默认 `https://api.openai.com`、`detection.engine` 默认 `regex`、`replacement.strategy` 默认 `placeholder`）。一旦用户想改这三项中的任何一项，改动就会完全失效。

### 建议

1. 修 `install.sh` / `install.ps1` 的配置模板，改为正确 schema；
2. 模板内容应**从 `configs/config.example.yaml` 裁剪**而来，而不是手写——避免再次漂移；
3. 加一条冒烟断言：安装后用生成的配置启动网关，`GET /healthz` 必须 200，且启动日志里的 `upstream=` / `engine=` / `strategy=` 与预期一致。

## 🔴 P0-2 · 配置未知键被静默忽略

### 现象

`internal/config/config.go:243` 用 `yaml.Unmarshal` 解析配置，**未启用严格模式**。yaml.v3 默认忽略结构体里不存在的键，且不报错。

```
$ llmate-gate --config <schema 错误的配置>
2026/09/15 20:05:58 [llmate-gate] listen=:8402 upstream=https://api.openai.com engine=regex strategy=placeholder ...
```

无任何告警，正常启动。

### 证据

同一份配置在「错误 schema」与「正确 schema」下启动日志**完全一致**（除 `--listen` 覆盖的端口）。

### 影响

这是 P0-1 无法被察觉的**根因**。项目在别处一贯执行「校验失败一律退出，绝不降级」（`config.go:3` 的包注释、§3.2 的 11 条校验），唯独对「未知键」放行——这与既定设计哲学不一致。

用户配置写错一个键名，不会得到任何反馈。

### 建议

改用严格解析：

```go
dec := yaml.NewDecoder(bytes.NewReader([]byte(expandEnv(string(raw)))))
dec.KnownFields(true)
if err := dec.Decode(c); err != nil { ... }
```

启动期一次性失败，符合项目既有约定。**建议与 P0-1 同批修**：先严格化，再修模板——否则严格化会让现存的错误模板立刻启动失败，反而暴露成回归。正确顺序是同时改、一起验。

## 🟡 P1-3 · `--uninstall` 不删 binary，且遇错即中断

### 现象

`scripts/install.sh` 的卸载分支（第 78-96 行）只做三件事：停 systemd 服务、删 unit 文件、`pkill` 进程。**从不删除 `$INSTALL_BIN`（`~/.local/bin/llmate-gate`）与 `$CONFIG`**。

并且脚本头部是 `set -euo pipefail`（第 15 行）：

```
$ bash scripts/install.sh --uninstall --binary ...
[install] 卸载 llmate-gate
Failed to connect to bus: No such file or directory      # 容器无 dbus
$ ls ~/.local/bin/llmate-gate                            # 残留仍在
-rwxr-xr-x 1 root root 13852669 ... /home/jzhli/.local/bin/llmate-gate
```

`systemctl` 一失败，`set -e` 直接中断，后续 `pkill`、日志、`exit 0` 都没执行。

另有一个独立问题：`--uninstall` 分支位于 binary 存在性检查（第 68 行）**之后**，所以不传 `--binary` 时卸载直接 FAIL：

```
$ bash scripts/install.sh --uninstall
[install][FAIL] 找不到 binary：/home/jzhli/LLMate-Gate/dist/llmate-gate-linux-amd64。请先 ./scripts/release.sh 编译，或用 --binary 指定。
```

而卸载根本不需要 binary 源文件。

### 对照：Windows 侧是正确的

`scripts/install.ps1:53-74` 的 `Do-Uninstall` 完整删除计划任务、桌面 LNK、`$InstallDir`，且 `if ($Uninstall) { Do-Uninstall }`（第 78 行）位于找 binary（第 80 行）**之前**。这正是「Windows 侧真机冒烟过（`0cea49b`）、Linux 侧从未真机跑过」的直接后果。

### 影响

Linux 用户执行卸载后，二进制仍在 `~/.local/bin`，且 `PATH` 里仍可调用；再次安装会在 `config.yaml` 已存在时跳过生成（见 P1-5）。用户会认为「卸载干净了」。

### 建议

1. 卸载分支前置到 binary 检查之前；
2. 补 `run rm -f "$INSTALL_BIN"`；
3. 对 `systemctl` / `launchctl` 调用加容错：`run systemctl --user disable --now "$SERVICE_NAME" || true`（服务不存在是卸载的正常情况，不应中断）；
4. 卸载结束打印「已删除哪些路径」清单，让用户可核对。

## 🟡 P1-4 · `--dry-run` 仍真实写盘

### 现象

`install.sh:45-51` 定义了 `run()` 包装器，dry-run 时只打印不执行。但**并非所有写操作都走了它**：生成默认配置用的是裸 `cat >`（第 103-118 行），生成 systemd unit 也是裸 `cat >`（第 127 行）。

```
$ bash scripts/install.sh --dry-run --binary ... --port 8401
  [dry-run] install -m 0755 ... /home/jzhli/.local/bin/llmate-gate   # ← 被拦住了
[install] 已安装 → /home/jzhli/.local/bin/llmate-gate
[install] 已生成默认配置 → /home/jzhli/.local/share/llmate-gate/config.yaml（请补 api_key）
  [dry-run] systemctl --user daemon-reload
  ...

$ stat -c '%y %n' ~/.local/share/llmate-gate/config.yaml
2026-09-15 20:05:39 ... /home/jzhli/.local/share/llmate-gate/config.yaml   # ← 真的写了
```

### 影响

`--dry-run` 的语义是「只看计划，不动系统」。用户在一次预演之后，系统中就多了一份被 P0-1 描述的错误配置——而这份配置存在，会让下次真装的 `--port` 失效（见 P1-5），形成连锁。

### 建议

把 `mkdir -p` 与两处 `cat >` 也纳入 `run()`；或者引入 `run_write <path> <<EOF` 形式的辅助函数，统一处理 dry-run 分支。

## 🟡 P1-5 · `--port` 与既有配置不一致 → 假失败

### 现象

`--port` 只影响两处：生成配置时的 `listen`（仅在文件不存在时生效）、以及健康检查的 URL。它**不校验已存在 `config.yaml` 里的 `listen`**，也不把 `--port` 传给启动命令（启动用的是 `--config "$CONFIG"`，第 181 行）。

真机复现：

```
$ bash scripts/install.sh --no-autostart --binary ... --port 8404     # 此时 config.yaml 已存在（listen: :8401）
[install] 已安装 → /home/jzhli/.local/bin/llmate-gate
[install] 已后台启动（PID=12，日志 ...）
[install] WARN 健康检查未通过（可能还在启动或端口被占用）             # ← 假失败
[install] 安装完成。

$ cat ~/.local/share/llmate-gate/stderr.log
... listening on :8401 (debug=true)
... server error: listen tcp :8401: bind: address already in use     # ← 用的是配置里的 8401，不是 8404
```

健康检查查的是 `:8404`，网关监听的是 `:8401`，**必然失败**。

两个附加问题：

1. 健康检查失败只打 `WARN`，脚本仍以 **0 退出**（第 189-193 行）——CI 或自动化调用方无法感知失败；
2. 提示语「可能还在启动或端口被占用」把真实原因（配置与参数不一致）掩盖了。

### 影响

用户改端口重装会得到一个「装好了但没起来」的状态，且日志在 `~/.local/share` 下不易发现。

### 建议

1. 启动时显式传端口：`nohup "$INSTALL_BIN" --config "$CONFIG" --listen ":${PORT}"`（`--listen` 已是支持的 flag，`main.go:49`），让参数优先于配置；
2. 或在配置已存在且 `listen` 与 `--port` 不一致时，明确提示「检测到既有配置使用 :X，本次将按 :Y 启动」；
3. **健康检查失败应返回非零退出码**，或在 `--no-autostart` 下明确区分「已启动成功」与「未通过健康检查」两种终态；
4. 健康检查失败时把 `stderr.log` 尾部贴给用户，而不是让用户自己去找。

## 🟡 P1-6 · 流式孤儿指标是死指标，且计算结果被丢弃

### 现象

`metrics.go:70-73` 定义并注册了 `llmate_stream_orphan_placeholders_total{endpoint}`，但**全仓无任何写入点**（仅 `metrics_test.go:26` 仪式性 `Inc()` 过一次，所以 CI 不会发现）。

真实计数在别处：`replacer/stream.go:11` 的 `var StreamOrphanTotal atomic.Int64`，由 `stream.go:131` 累加。

`proxy.go:531-533` 试图把它接进指标，但：

```go
if p.m != nil {
    orphanDelta := replacer.StreamOrphans() // 全局累计，近似计入
    _ = orphanDelta                          // ← 赋值后立即丢弃，从未写入 p.m.StreamOrphans
    p.m.RequestsTotal.WithLabelValues(...).Inc()
    ...
}
```

三个问题叠加：

1. 变量算出来了但被 `_ =` 丢弃；
2. 指标永远为 0，`/metrics` 上看到的孤儿数为假；
3. 变量名 `delta` 与实际语义不符——`StreamOrphans()` 返回的是**进程级累计值**，不是本次请求的增量。即便接上，按请求累加会重复计数。

### 影响

`Specs/00` §5.3 把「流式残留占位符」列为契约级可观测项，实际运维看不到。这个指标的真值恰恰是**流式还原正确性的关键信号**（孤儿意味着上游看到了未还原的哨兵串）。

### 建议

在 `replacer` 侧暴露可比较的计数接口，例如：

```go
// 返回当前累计值，调用方可自行做差
func StreamOrphanTotal() int64
```

在 `streamResponse` 里按请求前后取差：

```go
before := replacer.StreamOrphans()
... // 处理流
if d := replacer.StreamOrphans() - before; d > 0 {
    p.m.StreamOrphans.WithLabelValues(endpoint).Add(float64(d))
}
```

同时补一条集成测试：构造一个必然产生孤儿占位符的流（上游返回残缺哨兵），断言 `/metrics` 里该计数 > 0。现有测试只覆盖了 `replacer` 包内的原子变量，没有覆盖指标接线。

## 🟢 P2-7 · 请求体被重复全量读取

### 现象

`server.handleLLM`（`server.go:77-83`）先 `detectStream(r)` 把整个 body `io.ReadAll` 进内存，再用 `io.NopCloser(bytes.NewReader(body))` 回填 `r.Body`；随后 `proxy.Handle`（`proxy.go:112`）**又** `io.ReadAll(r.Body)` 读一遍。

### 影响

每个请求：两次全量读 + 两次字节切片分配 + 一次 `NopCloser` 包装。对大 prompt / 长上下文（Agent 场景常见）是纯粹浪费，且两处分配都随 body 线性增长。

### 建议

让 `handleLLM` 把已读出的 `body` 直接传给 `proxy.Handle`（改签名 `Handle(w, r, endpoint, stream, body []byte)`），或让 `detectStream` 返回 `io.ReadCloser` 供下游复用。前者更简单，且 `Handle` 内部本来就要 `io.ReadAll`。

> 注：`conversationID(r, r.Body)`（`proxy.go:110`）也接收 body 参数但当前实现未使用（`conversationID(r *http.Request, _ io.Reader)`），可在同一批清理。

## 🟢 P2-8 · 可仿真类型表在两处手工同步

### 现象

`config.go:356-365` 维护 `simulatableTypeOrder`（8 类），注释自述：

```
// ... 与 simulator.Generator.Fake 的 switch 保持一致。
```

而 `simulator/simulator.go:109` 的 `Fake` 是另一处独立维护的 `switch entityType`。

### 影响

新增一类可仿真实体时，若只改一处，会出现两种静默错误：配置校验通过但运行期 `Fake` 返回错误，或反之。两处相距 3 个包，靠注释约束不可靠。

### 建议

把权威表放在 `pkg/types`（与 `AllTypes()` 同处），或在 `simulator` 包导出 `SimulatableTypes() []string`，由 `config` 反向引用。`config` 已经依赖 `simulator`（`config.go:14` 已 import），改动成本低。

## 🟢 P2-9 · `gateway.upstream` 与 `upstreams[protocol=openai]` 语义重叠

### 现象

`main.go:226-243`：先由 `gateway.upstream` 构造 `openaiUp`，再用 `upstreams` 列表里 `protocol: openai` 的条目**整体覆盖**它。同一件事有两个配置入口，且后者静默覆盖前者。

同时 `config.Validate` 要求 `gateway.upstream` 非空——即使用户只想用 `upstreams` 声明全部上游，也必须保留这个其实不会生效的字段。

### 影响

用户可能同时写了两处且取值不同，实际生效的是 `upstreams`，但配置摘要（`config.String()`）打印的是 `gateway.upstream`，**打印值与实际值不一致**，排查时会误导。

### 建议

1. `config.String()` 打印实际生效的上游（`openaiUp.URL`）；
2. 或在 `Validate` 里加一致性告警：两处都配且不同时明确提示「以 upstreams 为准」；
3. 长期看可让 `gateway.upstream` 仅作 `upstreams` 的语法糖（未配 `upstreams` 时展开为一条 openai 上游），单一权威来源。

## 🔵 B-10 · 真对抗语料含重复样本

### 现象

`fixtures/cases_adversarial.jsonl` 声明 28 条，但存在成对重复：

| 重复组 | 文本 |
|---|---|
| `person_ethnic_adv-010` = `015` | 对接人买买提·阿凡提确认出席本次对接会。 |
| `person_compound_adv-011` = `016` | 本次合作由欧阳娜娜代表团队出面。 |
| `addr_abbrev_adv-012` = `017` | 出差：上海浦东张江园区 软件园 12 号楼 |
| `email_plus_adv-013` = `018` | Support: support+security@example.com （安全团队） |
| `ip_port_adv-014` = `019` | 测试服务器地址：10.0.0.1:8080，登录后进入调试模式。 |
| `mixed_real_adv-024` = `025` | 客户资料：李雷，电话… |
| `mixed_tool_adv-026` = `027` | `{"name": "send_email", ...}` |

**实际唯一文本约 15 条**。

### 影响

1. by-subset 的 `n_cases` 虚高（如 `person_name` 标称 4 条，实际 2 条），F1=0 或 1.0 的结论建立在小样本上；
2. 重复样本对 P/R 的贡献被放大一倍，评分权重失真；
3. 「28 条」这个数字会让读者高估语料覆盖面。

### 建议

1. 去重，或对重复项标注 `"dup_of": "xxx"` 由评估器按唯一文本聚合；
2. 在报告头部同时打印「声明条数 / 唯一文本数」；
3. 扩充到每个 subset 至少 15-20 条唯一文本，再发布 by-subset 结论。

## 🔵 B-11 · `expect: []` 把已知漏检固化进期望

### 现象

语料中有 4 条 `expect: []`：

```json
{"id": "phone_fmt_adv-004", "text": "联系电话：+86-186-1234-5678，仅工作时段接听。", "expect": [], "note": "known_weakness_unnormalized_phone_format"}
{"id": "idcard_mask_adv-028", "text": "员工张三的身份证号是 110101********8531，请核对。", "expect": [], "note": "real_world_masked_expect_miss"}
```

两类语义被混在同一个表达里：

- `idcard_mask_adv-028`：掩码身份证**不应该**被识别为完整身份证 → `expect: []` 合理，检出即 FP（报告里确实计了 FP=1）；
- `phone_fmt_adv-004/005/006`：`+86-186-1234-5678` 是**真实手机号**，只是当前引擎认不出 → `expect: []` 意味着「认不出算正确」。

### 影响

后一类的漏检没有计入 FN，**召回率被系统性抬高**（这 3 条若按「应检出」计，FN 会从 14 增至 17，R 从 0.6111 降至约 0.5645）。评估器把缺陷写成了期望，等于放弃了度量这项缺陷的能力。

### 建议

1. 区分两种语义：新增 `"expect_miss": true`（已知能力缺口，不计入 P/FN，但单独统计并展示）与 `"expect": []`（确实不该有 PII，检出即 FP）；
2. 报告里单列「已知能力缺口」小节，避免它们无声地稀释指标；
3. 这 3 条应驱动一个明确的决策：**是补 `+86` / 分隔符归一化，还是明确声明不支持该格式**。两者都可以接受，但不能是「默默地当它不该被检出」。
